# Mental model for hiveplotlib work

Shared knowledge every agent in the hiveplotlib harness needs. Loaded by all roles (Orchestrator, Code Engineer, Test Engineer, Docs Engineer, Notebook Author, Viz Critic, API Critic, Research Liaison, Verifier). When you reach for a default, a name, a quality bar, or a process choice, this is the source of truth. Defer to it.

If you find yourself disagreeing with a rule here, surface the disagreement to the user before acting. The skill is meant to be amended deliberately, not silently bypassed.

## Workflow rules

Process rules. Non-negotiable.

### 1. Plan before execute

No non-trivial code change starts without a plan. Plans live at `<repo>/.claude/plans/<topic>.md` for whatever repo the work is in (hiveplotlib work in `hiveplotlib/.claude/plans/`, wiki work in `hiveplotlib-llm-wiki/.claude/plans/`). Use the template at the harness's `.claude/templates/plan-template.md`. Plans are tracked in git, are the canonical reference for a piece of work, and persist across sessions. The conversation transcript is not the plan.

The Orchestrator's primary job is plan production. Specialists only run after a plan is accepted.

**Plans for any change that adds or modifies user-facing API must include an "API usage examples" section** with code snippets showing how the user will invoke the new or changed surface when the work is complete. The API Critic reviews these snippets during planning, before code is written, to catch ergonomic issues at the cheapest stage.

For trivial tasks (single-file edits, obvious one-line fixes, docstring tweaks): skip the plan, narrate intent in one sentence, proceed.

### 2. Replace-and-sweep is part of the change, not a follow-up

When introducing a new API that wraps or replaces an existing pattern, the same plan and the same PR include the sweep across all call sites:

- Notebooks (tutorials and gallery)
- Docstring examples
- README and gallery prose
- Install-instruction parity (if a new optional dep is involved)
- Reference links to autogenerated artifacts (e.g., metrics tables in autodoc)

Concrete example: when `from_networkx(node_graph_metrics=...)` shipped, every example notebook still computing degree via `nx.degree(...)` for the same purpose was a survivor that should have been swept in the same change.

Mechanism:

- During planning, the Orchestrator runs an audit: grep for the old patterns. The plan's "Patterns this replaces" section must list them or explicitly state "None."
- During execution, hits dispatch to the right specialist (notebooks → Notebook Author, docstrings → Docs Engineer, source/tests → Code Engineer).
- Post-execution, the Verifier greps for the old pattern. Survivors fail the run unless explicitly listed in the plan's `Holdouts` block with a reason.

### 3. Justify defaults from the user's workflow

When picking a default for any user-facing parameter, write one sentence in the plan explaining what the user is trying to do when they reach for this code. If the default doesn't match that workflow, change it.

Library-internal symmetry is not a justification. "It feels symmetric to default to `(True, False)`" loses to "users who care about in-degree and out-degree are already thinking directionally, so `directed=True` matches their workflow."

### 4. Demo the user-intended API for the data the user has

When a tutorial or gallery example shows users with NetworkX graphs, demo through `from_networkx`. When users have nodes/edges separately, demo raw `HivePlot`. Don't reach to lower-level alternatives (e.g., the converter functions) as the primary path in a tutorial just because they exist. Lower-level paths are for extension, edge cases, or users who need the seam — not the headline demo.

If demonstrating the user-intended path requires niche or complicated data that doesn't already live in `hiveplotlib.datasets`, **create a formal toy example there** (e.g., `hiveplotlib.datasets.example_<topic>`). Don't embed contrived data inline and don't skip the demo.

### 5. Naming follows user vocabulary, decided at planning time

Every plan has a "Naming audit" section. Check new parameter names, method names, class names, and user-facing prose against the vocabulary users would use, often borrowed from the dominant adjacent ecosystem (NetworkX terms when working with graphs, ML terms when working with embeddings, etc.). Pick names that match the user's vocabulary, not the engineer's.

Internal module/package names can stay engineer-flavored. Surface vocabulary flips first. Example: `graph_features` survives as an internal package while user-facing prose says "metrics."

The audit happens **before** code is written. Once shipped, names are expensive to change.

### 6. Plan-as-living-document

After every workstream or phase completes, the Orchestrator (or the executing specialist) writes the implementation summary into the plan's "Implementation log" section in the same turn the work completes. "Not yet started" placeholders for completed workstreams are bugs. The Verifier checks the log is up-to-date before allowing a workstream to be marked complete.

### 7. Critics auto-fix deterministic issues, propose taste calls

Verifier and Critic agents act differently based on the kind of issue.

**Auto-fix without asking:**

- Lint errors (ruff)
- Type errors (ty)
- Broken links
- Failing tests, after attempting a real fix (not "remove the test")
- Formatting violations
- Missing trailing newlines, etc.

**Propose only, with confidence tag, user triages:**

- Design choices ("this could be reorganized as...")
- Ergonomic suggestions ("consider flipping this default")
- Structural preferences ("this section feels redundant with that one")
- Naming preferences after-the-fact (the planning audit should catch these earlier)

The line is "objective wrongness" auto, "judgment call" propose. When in doubt, propose. Critics tag every proposed item with a confidence: `must-fix` / `worth-discussing` / `low-confidence`.

**Critics participate in planning, not just post-implementation review.** The API Critic reviews proposed API surface from a user-attempting-task perspective during planning and signs off on the plan's API usage examples section. The Viz Critic reviews planned visualization changes for partition discipline, color/alpha, and backend choice. Planning-phase critic findings amend the plan; post-execution critic findings follow the auto/propose split above.

### 8. Preserve user-friendly framing in docstring and prose rewrites

When rewriting a docstring or prose section, preserve the user-friendly lede first; layer new info on top. A docstring with more information that's harder to read is a regression. If the original framing was clear and approachable, the rewrite must remain clear and approachable.

### 9. Never commit code without explicit user review

The harness produces diffs, plans, and review artifacts. The user reviews and commits. Specialists never run `git commit` or `git push`. Even after the Verifier passes, the change is staged and surfaced to the user for review; commit happens only on explicit user approval. This is a hard rule, not a default. It applies in auto mode too. Plans, memory files, skill files, and template files in the harness repo can be written and edited by agents; production code, tests, docs, and notebooks in the consumer repo can be edited but never committed by an agent.

## Library invariants

Technical facts about hiveplotlib that don't change session-to-session. Treat as ground truth.

**Hive plots have 3 axes, almost always.** The default mental model is 3 axes, often with repeat axes (the karate club's 3-axes-with-repeats layout is canonical and produces 6 effective axis halves). 2 axes without repeats is essentially never useful — there is one toy demo notebook that uses it for pedagogical purposes and that's it. 4+ axes is a bug; use HivePlotMatrix (small multiples) instead. Partition design discipline matters: meaningful binary or ternary cuts (Medici vs. rest, low/medium/high), not numbered community-detection labels.

**Edge kwargs follow a configurable hierarchy.** Five named kwarg groups, default order from lowest to highest priority:

1. `all_edge_kwargs` (lowest, applies to every edge)
2. `clockwise_edge_kwargs`, `counterclockwise_edge_kwargs`, `repeat_edge_kwargs` (equal middle priority — they affect non-overlapping edge sets)
3. `non_repeat_edge_kwargs` (highest, all inter-group edges)

The order is stored on `HivePlot.edge_kwarg_hierarchy` and is user-reorderable. Conflicting kwargs trigger warnings; the higher-priority value wins. `plot()` call kwargs are deprioritized below the entire hierarchy. `Edges` instance kwargs are below those. `update_edges()` is the explicit per-pair override and bypasses the hierarchy without warning because the user is specifying directly. Each viz backend implements `rename_edge_kwargs()` to translate matplotlib-style kwargs to backend-specific ones. Canonical reference: `examples/edge_kwarg_hierarchy.ipynb`.

**The library is intentionally lightweight; everything beyond core is optional.** Core install is matplotlib + numpy + pandas. All viz backends and graph integrations ship as optional extras: `hiveplotlib[networkx]`, `hiveplotlib[bokeh]`, `hiveplotlib[holoviews]`, `hiveplotlib[plotly]`, `hiveplotlib[datashader]`. Imports are wrapped in try/except with helpful error messages so the missing-dep failure mode is graceful.

Tests are gated by markers: `@pytest.mark.networkx`, `@pytest.mark.bokeh`, `@pytest.mark.datashader`, `@pytest.mark.holoviews`, `@pytest.mark.plotly`. **Marker discipline is strict and CI-verified.** The CI pipeline runs subset-installs (e.g., installing only bokeh) and confirms that only the matching marker's tests run; everything else is skipped or fails-fast on missing deps. When adding code that touches an optional dep, the test marker is mandatory and CI will catch a missing one.

**Test discipline.** 100% coverage required (`--cov=src/hiveplotlib`). All warnings as errors. 7 parallel workers. Test files mirror source structure with `*_test.py` naming. Markers for optional deps (`@pytest.mark.networkx`, etc.).

**Code style.** ruff with 88-char line length for code, 120 for docstrings. Type checking via `ty` (currently pinned to 0.0.20). Pre-commit-friendly.

**Notebooks.** `examples/` is canonical source. `docs/source/notebooks/` and `docs/source/gallery_examples/` are auto-generated copies. Never edit those directly. Tutorials are storytelling; gallery is reference. Both have detailed skills at `hiveplotlib/.claude/skills/`.

## Prose voice

From the user's global rules. Applies to any text the reader sees: notebook markdown, README/docs prose, PR descriptions, commit message bodies.

- **No em-dashes (`—`).** Use commas, parentheses, semicolons, periods, or shorter sentences. The em-dash is the biggest "AI wrote this" tell.
- **No AI filler:** "delve", "moreover", "furthermore", "underscore", "in essence", "it's worth noting that", "let us consider", "as we can see", "in the realm of."
- **No throat-clearing preambles.** "First, let's discuss X" before discussing X adds nothing. Just discuss X.
- **No hedging meta-commentary.** "It is important to note that X" is just "X."
- **Library helpers are tools, not characters.** Just use `flexitext`, `seaborn`, `numpy.random.default_rng`. Don't introduce them with a paragraph.
- **Direct, slightly informal voice.** "Let's look at what happens when we sort by degree" beats "We shall now examine the consequences of sorting by degree."
- **Length discipline.** If a section runs noticeably longer than its closest existing sibling for comparable scope, cut prose. Reader patience is finite; respect it.

Code comments are exempt. Focus is text the reader sees.
