# Expertise: API Critic

Curated playbook of what this role has learned. **Not a log.** Edit existing entries when a new observation refines or supersedes them; add new entries only when truly new ground is covered; remove entries that no longer earn their place. Every entry comes from a real failure or repeated success (not invented advice), follows the entry shape (lead + body, no originating-plan citation), and stays lean (soft target ~60-90 words) per mental-model rule 11.

## Patterns to reach for

- **Walk the new surface as a user typing the class name and hitting tab; read the resulting tooltip.** First-pass check for any new public surface. Catches discoverability cliffs (a user expecting `Class.from_networkx` finds only `_partition` / `_variable_sweep` / `_tags` siblings) and signature-tooltip lies (a classmethod lifts list-shaped params into the signature but leaves required singleton companions in `**kwargs`) that code-only diff review misses.

- **When a plan proposes multiple new "modes" for one agent, check whether each mode has independent function or is a parameter switch.** A real mode differs in inputs, outputs, or decision shape (`initial-plan` produces a new file; `amend-plan` reads an existing file and edits its amendments section). A parameter switch reuses an existing mode's function with a different consumer or path; collapse it rather than coining a sibling.

- **After a planning-mode collapse of N modes into N-1, post-impl must sweep for residual mentions of the dropped mode name.** The Modes section closes cleanly, but the dropped name survives in parenthetical lists, Output descriptions, error messages, or example invocations, which describe behavior rather than enumerate modes. Grep the whole file before declaring clean.

- **Sweep adjacent surfaces (roadmap docs, vision pages) after tearing out a public API; they don't track the implementation grep.** Roadmap / vision / future-work pages describe a promised capability by *intent*, not *name*, so the source/autodoc/notebook grep doesn't reach them. Include them explicitly in the post-impl sweep; look for stale "we could add X" prose where X just shipped.

- **Walk the first-error experience for the muscle-memory transition path.** When a public API changes shape (classmethod → keyword-only constructor parameter), the error a user typing the prior shape hits determines whether the transition feels supported or hostile. Recovery-oriented `ValueError`s cover validator-caught cases, but a prior-shape call binding positionally to a *different* parameter fails downstream uncaught. A defensive `isinstance(nodes, nx.Graph)` guard with a recovery message closes the gap; default low-confidence for unshipped pre-release surfaces, flag with the actual traceback.

- **For an ecosystem-specific duck-type guard, audit false-positives by walking the actual sibling libraries' method names, not by eyeballing "the predicate looks specific enough."** Single-method probes typically collide across libraries; two-method probes often pin to one ecosystem because the second method's *name* diverges even when the capability matches. Walk each candidate library's method names and write the per-library outcome into the post-impl review even when the predicate passes. For example, `hasattr(nodes, "is_directed") and hasattr(nodes, "is_multigraph")` pins to networkx because the second name diverges: igraph `has_multiple`/`is_simple`, graph-tool no `is_multigraph`, rustworkx `multigraph` as an attribute; an `is_directed`-only probe collides with igraph.

- **When a plan's headline surface is an error string spanning two entry points, verify each remedy names a kwarg that exists on the entry point the user actually called.** A message authored against the high-level surface (`HivePlot(..., graph_directed=...)`) is wrong verbatim when it also fires on a low-level surface lacking that kwarg (`compute_graph_metrics(graph, ...)`); branch the message on entry point, don't share one string. Also check the remedy's *scope*: "split into two calls" undersold a resolution that also required rebuilding the graph per call (directed for `in_degree`, undirected via `to_undirected()` for `triangles`). For error-string-as-API plans, recommend the post-impl pass read raised message text per example, not just assert the exception type.

## Anti-patterns

- **Don't review a plan that cites an originating incident without verifying the incident's current state in the working tree.** The tree can move between drafting and review (an unrelated commit corrects part of the issue). When the plan cites a `file:line` as the incident, read that line; if state shifted, recommend updating the example (footnote the pre-correction state as motivation) or amending the done-when.

- **Don't treat "mechanical propagation" as exempt from review.** When a sibling class gains a surface mirroring another's API (`HivePlotMatrix` mirroring `HivePlot`'s graph-features API), it's still a fresh first encounter for the sibling's users; walk it from scratch as if the parent surface didn't exist.

- **Apply the first-encounter-discoverability lens to reader-facing harness surfaces (CHANGELOG entries, rule prose, agent-report shapes), not just Python APIs.** A CHANGELOG reader, an agent reading an amended rule on first invocation, and a dispatching session parsing a report all share the single-shot encounter. Probe: "what does the reader land on in the first sentence, and is the load-bearing behavior there or three sentences in?" For process-rule workstreams (carve-outs, constraint bullets, contrastive phrasing), walk three concrete future-agent scenarios end-to-end: canonical + debugging-edge + gameable-rationalization.

- **For harness-self plans whose "API" is an agent's report format, audit the report vocabulary as if it were a Python signature: every new token forces dispatching sessions to learn a second axis.** When a plan proposes a new state on an existing report line, check whether an existing channel already carries the same information. qa-engineer's `Status: pass | fail | propose` already encodes "green but reviewer concerns surfaced" via `propose`; a new sibling state that demotes `Status` to `propose` for the same fact creates two parallel channels. Redefine the existing token (`pass` = zero warnings), route through it.

- **When extending a numbered taxonomy, the new entry's grammatical shape must match the existing entries', not just their content domain.** Existing entries develop micro-conventions (length, imperative voice, cross-reference style, parenthetical presence) a reader registers as local grammar; a breaker reads as more important on grammatical weight alone. Render the taxonomy as a flat list and read aloud; the new entry should be indistinguishable in cadence. Trim parentheticals / follow-on sentences the others don't carry.

- **When a catastrophic-severity case has no slot in the routine state machine, prefer an out-of-band escape-hatch report shape over adding a fourth value to every agent's `Status:` line.** A fourth value fails *unevenly*: work-agents have `complete | partial | blocked`, qa-engineer `pass | fail | propose`, critics `clean | propose`; four-of-nine have no slot. An escape-hatch template (uppercase `STATUS: BLOCKED` standalone first line, *replacing* the routine report) works uniformly; case and position signal "out-of-band severity, not routine state."

- **When a harness rule fans out to N agent definitions, harden cross-file consistency from "consistent" to "verbatim-equal" on the load-bearing tokens.** "Consistent" admits paraphrase; "verbatim-equal" doesn't. Risk concentrates on tokens the dispatching session and downstream agents pattern-match against (report headers, verb pairs, rule citations); paraphrase forces them to learn N variants of one token. Identify the tokens in planning mode; recommend the Quality bullet name them with verbatim-equality (e.g. `STATUS: BLOCKED` and `STOP and surface`).

- **For harness-self plans, distinguish "owning-specialist axis" from "scope axis" in carve-out rules.** Exemptions key on (a) which specialist owns the workstream or (b) the scope; the two diverge on code-engineer-led docs work (specialist != docs-engineer, scope IS docs) and docs-engineer-led API renames (specialist == docs-engineer, scope is API). User directives pin scope; orchestrator plans shorthand to specialist because grepping it is mechanically simpler. Pivot carve-out terms to scope nouns (`docs-scope workstream`, not `docs-pass workstream`), defined against the workstream brief.

## Gotchas

- **Planning-mode proposals built on unverified identity / aliasing claims need empirical verification before they ship.** An `id()`-based key change rests on an implicit claim about which inner objects are aliased across which construction paths; shipping unchecked can widen for narrower cases than intended. If post-impl shows the dedup doesn't trigger for the natural-constructor case, read the construction chain for the *one* attribute level whose identity survives. For example, `Edges._validate_edge_data` rebuilds the outer dict so `(id(hp.nodes), id(hp.edges._data))` isn't aliased across `HivePlot(nodes, edges)`; the inner DataFrames are, so the robust key is `(id(hp.nodes), frozenset(id(df) for df in hp.edges._data.values()))`.

- **When adjudicating "accept narrow vs. widen further" for a perf-only fix, weight notebook English as the tiebreaker.** The bounded-worst-case argument (Nx slowdown, values identical) makes the fix sound deferrable. But if user-facing prose already promises the wider behavior, the prose-vs-code mismatch is a correctness concern in the api-critic's lane; pick recommend-follow-up over accept-as-is. Real case: notebook prose promising "computed once on shared data" that a narrower dedup didn't deliver.

- **After a tuple-shaped identity key is widened to a set-shaped one, run the "what does collapsing repeated ids change?" check before signing off.** Tuple `(id(a), id(b))` carries multiplicity and order; `frozenset({id(a), id(b)})` loses both. Order loss is usually wanted; multiplicity loss is the one to inspect. Walk natural construction paths; if none produce same-object-under-multiple-keys aliasing, log the pathological case low-confidence with a `tuple(sorted((tag, id(df)) for ...))` fix sketch (e.g. `Edges(data={"tag_a": df, "tag_b": df})` collapses to one element).

- **A vocabulary refactor that swaps a one-token noun for a multi-token noun-phrase breaks parallel-clause symmetry; flag the rare parallel-construction sites at planning time, not post-impl.** Replacing `(nodes, edges)` with "the `nodes` and `edges` parameters" reads cleanly on error messages, ledes, and `:raises:` lines. Friction concentrates where the original was *paired with another one-token noun in a parallel clause*: "the `(nodes, edges)` initialization defaults to ... ; the `graph` initialization defaults to ..." goes asymmetric because the "and" in the first half competes with the parallel separator. Recommend the surrounding sentence shape also change (possessive-noun "the X initialization" → participial "when initialized with X") so the parallel form survives.

- **When a vocabulary-refactor workstream defers a user-facing sub-surface ("X is docs-engineer's later call"), the post-impl review is the deferral-collection moment, not a free pass to leave it deferred.** A scope of "source + tests + notebooks" that defers CHANGELOG, migration guide, or blog notebook tends to ship stale vocabulary because no follow-up dispatch gets created. When qa-engineer pre-flags `worth-discussing`, default to **uphold-and-escalate** (must-fix) when (a) the deferred artifact ships with the release, (b) the literal phrase load-bears on the user's mental model, (c) the fix is a small mechanical word-swap with no rendering risk.

- **Done-when criteria are the post-impl contract; an unmet Done-when item upgrades qa's `worth-discussing` to `must-fix`.** Workstreams whose dispatch brief enumerates a subset of touched files drop the un-enumerated edit silently; qa often catches it but tags `worth-discussing` because it reads Files and Implementation log without cross-referencing Done-when line-by-line. The post-impl critic IS the agent reading Done-when as the binding contract; walk each bullet against the Implementation log and shipped diff before signing off.

- **For post-impl review on a workstream specifically motivated by closing a semantic-coherence gap from a prior workstream, the resolution-verdict is the load-bearing output; treat it as mandatory and frontload it above the routine surface-walk.** Read the prior workstream's failure-mode, then walk the diff asking "is this exact failure mode now closed?" and "does the new surface promise more than the closure, and if so does it deliver?" Forced binary (yes / yes-with-caveats / no) plus a one-paragraph rationale, frontloaded; routine friction list lands beneath.

- **reST emphasis spans do not parse inline-literal markup, so prose-polish fixes nesting `` ``token`` `` inside `*...*` render backticks literally.** Workable shape: plain text inside emphasis (`when graph= is provided`) with trailing `=` doing the kwarg-signaling, the surrounding parenthetical clarifying kwarg vs. ordinary prose. When the prefix is a cluster-level header rather than a per-param qualifier, append the literal "sub-family" to disambiguate.

- **When a wrapper omits a graph-type guard because "NetworkX will raise anyway," verify NetworkX actually raises rather than computing a silently-different result.** The friendly-guard pattern (`if graph.is_multigraph(): raise ValueError(...)`) gets treated as cosmetic, but breaks when the underlying NetworkX function doesn't raise on the disallowed type, instead converting via `to_scipy_sparse_array` and producing surprising-but-numeric output. The metric-table classifier probes for `(ValueError, NetworkXException)`; a silently-computing wrapper renders as no constraint, the user sees no warning, the value flows to the plot. Bright-line check: read the NetworkX source for explicit `is_multigraph()` / `is_directed()` checks; if absent, the wrapper needs its own guard to honor the done-when.

- **The `:raises:` block is the load-bearing user surface for catchable errors; mentioning the exception type in free-form prose is not equivalent.** Sphinx renders `:raises:` as a styled separate block; prose explains *why* the constraint exists, `:raises:` enumerates *what to catch*. When prose mentions "raises NetworkXUnfeasible if the graph contains a cycle" but the `:raises:` block lists only the wrapper's own ValueError, a user looking up "what does this throw" gets an incomplete answer. Post-impl, walk every wrapper that delegates a raise to NetworkX and verify `:raises:` lists every distinct exception type the user can hit. Real case: prose mentioned `NetworkXUnfeasible` for cyclic input while the `:raises:` block listed only `ValueError`.
