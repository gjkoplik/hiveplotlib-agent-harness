# Expertise: API Critic

Curated playbook of what this role has learned. **Not a log.** Edit existing entries when a new observation refines or supersedes them; add new entries only when truly new ground is covered; remove entries that no longer earn their place. Every entry earns its line by tracing to a real failure or repeated success.

## Patterns to reach for

- **Walk the new surface as a user typing the class name and hitting tab; read the resulting tooltip.** Discoverability cliffs (a user expecting `Class.from_networkx` and finding only `_partition` / `_variable_sweep` / `_tags` siblings) and signature-tooltip lies (a classmethod that lifts list-shaped parameters into the signature while leaving required singleton companions buried in `**kwargs`) both disappear from code-only diff review but surface immediately in tab-completion simulation. Make this the first-pass check for any new public surface; if multiple workstreams in a row earn findings from this simulation, that confirms the pattern. *Learned:* hiveplotlib GitLab #46 Workstream F shipped three sibling `HivePlotMatrix.from_networkx_*` classmethods without a discoverability stub (caught by tab-completion sim, became the centerpiece of Workstream G). Workstream G planning-mode review caught a two-of-four signature lift on `from_networkx_variable_sweep` that would have made the tooltip claim "you only need a list" when the underlying method requires a singleton companion in two of three sub-modes; the planning-mode finding flipped the implementation to the full four-parameter lift before code was written.

- **When a plan proposes multiple new "modes" for one agent, check whether each mode has independent function or is a parameter switch.** A real mode differs in inputs, outputs, or decision shape (e.g. `initial-plan` produces a new file; `amend-plan` reads an existing file and edits its amendments section). A parameter switch reuses an existing mode's function with a different consumer or path (e.g. "harness-meta" as initially proposed: same as `initial-plan` but with plans living at `agent-harness/.claude/plans/`). Collapse parameter switches into the existing modes; coining a sibling mode multiplies the surface area dispatching sessions must remember. *Learned:* `orchestrator-on-emergent-work` planning review collapsed `harness-meta mode` into a consumer parameter on `initial-plan` and `amend-plan`, dropping a name and a workflow subsection.

- **After a planning-mode collapse of N modes into N-1, post-impl review must sweep for residual mentions of the dropped mode name.** Treat the post-impl pass as the replace-and-sweep audit for the dropped name. A planning-mode collapse closes one surface (Modes section names two, not three), but the dropped name often survives in parenthetical lists, Output descriptions, error messages, or example invocations because those sections describe behavior rather than enumerate modes. Grep the whole file for the dropped name before declaring the post-impl review clean. *Learned:* `orchestrator-on-emergent-work` shipped with the Modes section correctly enumerating two modes, but `orchestrator.md:34`'s Output section retained "harness-meta work to `agent-harness/.claude/plans/`" as a work-category label, inventing a parallel three-way taxonomy in the same file that committed to two modes plus a consumer parameter. The qa-engineer caught this as worth-discussing; the post-impl critic re-classified to must-fix.

## Anti-patterns

- **Treating "mechanical propagation" as exempt from review.** When a sibling class gains a surface that mirrors another class's API (e.g. `HivePlotMatrix` mirroring `HivePlot`'s graph-features API), the new surface is still a fresh first encounter for users of the sibling class. Walk it from scratch as if the parent surface didn't exist; don't skim the diff and call it propagation-clean. *Learned:* the same Workstream F was framed as "API propagation, not redesign" in the plan; that framing made the dispatcher skip post-impl api-critic review entirely. The harness now treats this explicitly (mental-model rule 7, qa-engineer step 12, plan template post-impl placeholder).

## Gotchas

- **Planning-mode proposals built on unverified identity / aliasing claims need empirical verification before they ship.** When a planning-mode finding proposes a Python-`id()`-based key change (e.g. "widen `id(hp.edges)` to `id(hp.edges._data)` to catch shared-data cases"), the proposal often rests on an implicit empirical claim about which inner objects are aliased across which construction paths. Implementing the proposal without checking the claim can ship a widening that only fires for narrower cases than the brief implied. If the post-impl test-engineer surfaces "the dedup actually doesn't trigger for the natural-constructor case", the right next move is to read the chain (`A.__init__` -> rewrap call -> `B.__init__` -> `_validate_data`) and identify the *one* attribute level whose identity actually survives, then propose the further widening as Workstream H. *Learned:* hiveplotlib GitLab #46 Workstream G shipped `(id(hp.nodes), id(hp.edges._data))` as the dedup key based on a Workstream-F planning-mode finding; empirically `Edges._validate_edge_data` always builds a fresh outer dict so `id(hp.edges._data)` is not aliased across the `HivePlot(nodes, edges)` natural-constructor case. The inner DataFrames within `_data` ARE aliased through the rewrap (assignment is by reference); the right key for full reach is `(id(hp.nodes), frozenset(id(df) for df in hp.edges._data.values()))`. Cross-checked with the notebook prose: the existing `examples/hpm_generic.ipynb` markdown cell promises "the metric is computed once on the shared source data" which the narrower widening doesn't actually deliver. Recommended Workstream H to close the gap.

- **When adjudicating "accept narrow vs. widen further" for a perf-only fix, weight notebook English as the tie-breaker.** The bounded-worst-case argument (Nx slowdown for N cells; metric values stay identical) makes the perf-only fix sound deferrable. But if existing user-facing prose already promises the wider behavior (notebook markdown describing "computed once on shared data" when the code computes per-cell), the prose-vs-code mismatch is itself a correctness concern in the api-critic's lane. Pick (b) recommend-follow-up rather than (a) accept-as-is when the gap exists. *Learned:* same hiveplotlib GitLab #46 Workstream G adjudication. The dedup widening covers same-HP-twice and explicit-aliasing but not the natural constructor case the notebook's English already describes. The notebook's overpromise made (b) the right call even though the per-call cost is bounded.

- **After a tuple-shaped identity key is widened to a set-shaped one, run the "what does collapsing repeated ids change?" check before signing off.** A tuple `(id(a), id(b))` carries multiplicity and order; `frozenset({id(a), id(b)})` loses both. The order loss is usually wanted (dict insertion order across tags shouldn't break dedup); the multiplicity loss is the one to inspect. Concretely: if a user could construct an inner container where the same object appears under multiple keys, the frozenset collapses those into one element and admits dedup collisions with a sibling container that only has the object once. Walk the natural construction paths and confirm none of them produce that aliasing; if none do, log the residual case as low-confidence with a "switch to `tuple(sorted((tag, id(df)) for ...))`" fix sketch in case it surfaces. *Learned:* hiveplotlib GitLab #46 Workstream H widened the dedup key from `(id(hp.nodes), id(hp.edges._data))` to `(id(hp.nodes), frozenset(id(df) for df in hp.edges._data.values()))`. The contrived case `Edges(data={"tag_a": df, "tag_b": df})` (same DataFrame under two tags) collapses to a single frozenset element and would dedup-collide with a `{"tag_a": df}`-only sibling. Verified via `Edges._validate_edge_data` and `HivePlot.add_edges` that nothing in the natural construction paths produces this aliasing; logged as low-confidence rather than must-fix. The bag-vs-set check is cheap; it confirms the residual is pathological rather than realistic before the dedup contract ships.
