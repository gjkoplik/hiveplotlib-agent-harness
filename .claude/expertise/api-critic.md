# Expertise: API Critic

Curated playbook of what this role has learned. **Not a log.** Edit existing entries when a new observation refines or supersedes them; add new entries only when truly new ground is covered; remove entries that no longer earn their place. Every entry earns its line by tracing to a real failure or repeated success.

## Patterns to reach for

- **Walk the new surface as a user typing the class name and hitting tab; read the resulting tooltip.** Discoverability cliffs (a user expecting `Class.from_networkx` and finding only `_partition` / `_variable_sweep` / `_tags` siblings) and signature-tooltip lies (a classmethod that lifts list-shaped parameters into the signature while leaving required singleton companions buried in `**kwargs`) both disappear from code-only diff review but surface immediately in tab-completion simulation. Make this the first-pass check for any new public surface; if multiple workstreams in a row earn findings from this simulation, that confirms the pattern. *Learned:* hiveplotlib GitLab #46 Workstream F shipped three sibling `HivePlotMatrix.from_networkx_*` classmethods without a discoverability stub (caught by tab-completion sim, became the centerpiece of Workstream G). Workstream G planning-mode review caught a two-of-four signature lift on `from_networkx_variable_sweep` that would have made the tooltip claim "you only need a list" when the underlying method requires a singleton companion in two of three sub-modes; the planning-mode finding flipped the implementation to the full four-parameter lift before code was written.

- **When a plan proposes multiple new "modes" for one agent, check whether each mode has independent function or is a parameter switch.** A real mode differs in inputs, outputs, or decision shape (e.g. `initial-plan` produces a new file; `amend-plan` reads an existing file and edits its amendments section). A parameter switch reuses an existing mode's function with a different consumer or path (e.g. "harness-meta" as initially proposed: same as `initial-plan` but with plans living at `agent-harness/.claude/plans/`). Collapse parameter switches into the existing modes; coining a sibling mode multiplies the surface area dispatching sessions must remember. *Learned:* `orchestrator-on-emergent-work` planning review collapsed `harness-meta mode` into a consumer parameter on `initial-plan` and `amend-plan`, dropping a name and a workflow subsection.

- **After a planning-mode collapse of N modes into N-1, post-impl review must sweep for residual mentions of the dropped mode name.** Treat the post-impl pass as the replace-and-sweep audit for the dropped name. A planning-mode collapse closes one surface (Modes section names two, not three), but the dropped name often survives in parenthetical lists, Output descriptions, error messages, or example invocations because those sections describe behavior rather than enumerate modes. Grep the whole file for the dropped name before declaring the post-impl review clean. *Learned:* `orchestrator-on-emergent-work` shipped with the Modes section correctly enumerating two modes, but `orchestrator.md:34`'s Output section retained "harness-meta work to `agent-harness/.claude/plans/`" as a work-category label, inventing a parallel three-way taxonomy in the same file that committed to two modes plus a consumer parameter. The qa-engineer caught this as worth-discussing; the post-impl critic re-classified to must-fix.

- **Sweep adjacent surfaces (roadmap docs, vision pages) after tearing out a public API; they don't track the implementation grep.** When a workstream removes shipped (or planned-to-ship) public methods, the implementation grep (`src/*.py`, `docs/source/autodoc/`, `examples/*.ipynb`) catches the user-facing call sites and the autodoc surface. But "roadmap" or "vision" or "future-work" pages live in a separate documentation lineage and describe a promised capability rather than a current entry point; the implementation grep doesn't reach them because they don't reference the method *name*, they reference the *intent*. Post-impl sweep should explicitly include roadmap-style pages and look for stale "we could add X" prose where X is the capability just shipped. *Learned:* hiveplotlib GitLab #46 Workstream I tore out `from_networkx*` and consolidated onto `HivePlot(graph=...)`; the source/autodoc/CHANGELOG grep returned zero hits, but `docs/source/roadmap.rst:50` retained "we could add a static method `HivePlot.from_networkx(G: nx.Graph)`" as an open roadmap bullet because the capability landed via a constructor parameter rather than the proposed static method, and the source grep doesn't match prose that describes the future-tense version. Both qa-engineer and api-critic flagged independently.

- **Walk the first-error experience for the muscle-memory transition path.** When a public API changes shape (e.g., classmethod → keyword-only constructor parameter), users transitioning from the prior shape will type the prior shape and hit *some* error. The error they hit determines whether the transition feels supported or hostile. The locked recovery-oriented `ValueError` messages cover the cases the new validator catches, but they don't catch the case where the prior-shape call binds positionally to a *different* parameter and fails downstream. Specifically: if v0.27 shipped `HivePlot.from_networkx(g, ...)` and v0.28 ships `HivePlot(*, graph=...)`, then `HivePlot(g, ...)` silently binds `g` to `nodes` (positional) and the failure surfaces deep in `add_nodes` as a confusing `AttributeError`. The validator block at the top of `__init__` doesn't fire because `nodes is not None`. A defensive `isinstance(nodes, nx.Graph)` guard with a recovery message ("`graph=` is keyword-only; rewrite as `HivePlot(graph=...)`") would close this gap, at the cost of an optional-import dance. Flag this in post-impl review with the actual `AttributeError` traceback so the user can adjudicate the cost-of-fix; default to low-confidence because the muscle-memory population is small for any unshipped pre-release surface, but the cost-of-fix is also small for a shipped public API. *Learned:* hiveplotlib GitLab #46 Workstream I post-impl. The `HivePlot.from_networkx` shape never tagged a release so the muscle-memory population is limited to in-flight branch users, which is why I logged this low-confidence rather than worth-discussing.

## Anti-patterns

- **Reviewing a plan that cites an originating incident without verifying the incident's current state in the working tree.** Plans tend to be drafted against a snapshot ("the test at `tests/foo_test.py` ships with this bug today") and the working tree can move between drafting and review (an unrelated commit corrects part of the issue, leaving a residue). The planning-mode reviewer who walks the plan's examples without re-reading the cited file ratifies the snapshot's framing, including the parts that no longer match reality, and the resulting audit-machinery the plan proposes ends up calibrated against a state the repo isn't in anymore. Practical move: when the plan's "Patterns this replaces" or "Proposed (planner)" section cites a specific file:line as the originating incident, read that file:line as part of the review. If the cited state has shifted, flag the shift in the review and recommend either updating the plan's example to match current state (with a footnote naming the pre-correction state as motivation) or amending the plan's done-when language to handle the asymmetric state the working tree now produces. *Learned:* `rationalization-as-smell` planning-mode review. The plan's Example 2 described a qa-engineer report excerpt with both audits firing together (test-name-contract mismatch + rationalization-marker hit at the same file:line). The actual test at `tests/hiveplot_matrix_test.py:2867-2893` had been corrected — the test body now calls the named `from_partition` method — but the rationalization paragraph still ships at lines 2874-2876 with the marker phrase "to keep". Workstream B's done-when language correctly handles the asymmetric state (`pass` allows `worth-discussing` rationalization-marker hits when not co-located with test-name-contract mismatches), but the Example-2 shape no longer occurs in the repo and the reviewer needed to flag that explicitly so a future qa-engineer running the audit doesn't halt under rule 16 expecting the Example-2 shape.

- **Treating "mechanical propagation" as exempt from review.** When a sibling class gains a surface that mirrors another class's API (e.g. `HivePlotMatrix` mirroring `HivePlot`'s graph-features API), the new surface is still a fresh first encounter for users of the sibling class. Walk it from scratch as if the parent surface didn't exist; don't skim the diff and call it propagation-clean. *Learned:* the same Workstream F was framed as "API propagation, not redesign" in the plan; that framing made the dispatcher skip post-impl api-critic review entirely. The harness now treats this explicitly (mental-model rule 7, qa-engineer step 12, plan template post-impl placeholder).

- **Apply the first-encounter-discoverability lens to reader-facing harness surfaces (CHANGELOG entries, rule prose, agent-report shapes), not just Python APIs.** The "walk the new surface as a user typing the class name" pattern generalizes: a CHANGELOG reader scanning entries for the first time, an agent author reading an amended rule on first invocation, and a dispatching session parsing a report on first run all share the same single-shot encounter property. The friction symptom is also the same: a reader who has to assemble the right answer across multiple cross-references rather than getting it front-loaded in the first encounter. Practical probe: for each entry / rule body / report shape, ask "what does the reader land on in the first sentence, and is the load-bearing behavior there or three sentences in?" If load-bearing behavior is buried behind implementation detail (rule numbers, structural facts, taxonomy size), invert to behavior-first. Same probe catches procedural rules that state a mapping without sequencing the lookup (rule 13's "Target file by consumer" mapping benefits from an explicit "Before filing, check the plan path" prefix). For process-rule workstreams specifically (carve-outs added to agent definitions, new constraint-block bullets, contrastive exception phrasing), the strongest discoverability test is to walk N concrete future-agent scenarios end-to-end: name the dispatch context, the workflow step the agent reaches when it hits the new rule, and the exact failure shape the rule is meant to prevent. Three scenarios is typically enough to surface most friction (the canonical case + one debugging-edge case + one gameable-rationalization case); fewer and you miss the gameable-rationalization shape, more and you start re-stating the same scenario. *Learned:* `harness-changelog-and-line-endings` planning-mode review caught front-loaded structural detail across CHANGELOG / rule prose / agent-report surfaces; `make-targets-exclusively` post-impl review walked three named future-agent scenarios (autodoc update, full-suite verification, single-failing-test debug) and that triple was what turned a "the rule reads okay" pass into specific findings about pytest-modifier coverage gaps and constraint-bullet stylistic inconsistency.

- **For harness-self plans whose "API" is an agent's report format, audit the report vocabulary as if it were a Python signature: every new token forces the dispatching session to learn a second axis.** When the plan proposes a new state on an existing report line (e.g. `Docs build: pass-with-warnings` alongside `pass | fail | skipped`), check whether an existing channel already carries the same information. The qa-engineer's top-level `Status: pass | fail | propose` already encodes "everything green but reviewer concerns surfaced" via `propose`; a new sibling state on a sub-line that demotes `Status` to `propose` for the same underlying fact creates two parallel ways to communicate one thing. Recommend redefining the existing `pass` token (zero warnings, not just "build succeeded") and routing the concern through the existing `propose` channel rather than minting a new state. The naming-audit framing of "sibling of `pass | fail | skipped`" hides the real sibling relationship to `Status: propose`. *Learned:* `qa-engineer-docs-warning-posture` planning-mode review. The Orchestrator's plan proposed `pass-with-warnings` as a fourth value on the `Docs build:` line; the rejection rests on the fact that `Status: propose` is the existing umbrella for "build worked, debt surfaced" and the new token's existence forces every dispatcher and downstream qa-engineer to learn a second redundant axis. The token's naming-audit rejected `propose` for "token overlap" — the correct reading was that the overlap is the *reuse signal*, not the friction to avoid.

- **When extending a numbered taxonomy (rule 16 (a)'s six trigger bullets, rule 16 (c)'s five anti-action bullets), the new entry's grammatical shape must match the existing entries' shape, not just the entries' content domain.** Existing taxonomy entries develop their own micro-conventions (length, imperative voice, cross-reference style, parenthetical presence/absence) that a reader registers as the taxonomy's local grammar even without consciously naming the convention. A new entry that breaks the local grammar reads as more important than its siblings on grammatical weight alone, which over-weights it on first scan regardless of its semantic weight. Post-impl probe: render the taxonomy as a flat list and read each entry aloud; the new one should be indistinguishable in cadence from the existing entries. If the new entry carries a parenthetical that the others don't, or a follow-on sentence that the others don't, propose trimming to match. Cross-references between sibling sub-sections of the same rule are implicit and don't need explicit "see (c)" prose unless the existing entries already carry such pointers. *Learned:* `rationalization-as-smell` Workstream A post-impl. The new (a) bullet at SKILL.md:271 carried a parenthetical AND a follow-on sentence ("When this trigger fires, the failure mode is silent substitution plus in-artifact rationalization; see (c) for the anti-action enumeration"), making it visibly longer than the other six (a) bullets (each one line, no follow-on sentence). Sibling case: the new (c) entries at SKILL.md:282-283 used noun-phrase headers ("**No silent substitution.**") while the existing five (c) entries used imperative phrases hanging off the "do NOT:" lede ("Run destructive ops...", "Retry a failing test..."). Read straight through, the list now mixes grammars ("do NOT: ... no silent substitution") creating a soft double-negative. Both findings landed as worth-discussing; the lesson is to flag the grammatical-shape mismatch in planning-mode for any taxonomy extension and accept it as worth-discussing rather than must-fix unless the mismatch genuinely garbles the rule.

- **When a catastrophic-severity case has no slot in the existing routine state machine, prefer an out-of-band escape-hatch report shape over a fourth-value enumeration addition.** Sibling case to the "no new tokens on the routine line" lesson, but for the inverse situation: the rare case is genuinely outside the routine state machine's vocabulary and needs visual loudness the routine line can't carry. The fail mode of the naive resolution ("add a fourth value to every agent's `Status:` line") is *uneven reuse*: work-agents have `complete | partial | blocked` and the new value reuses `blocked`, but qa-engineer has `pass | fail | propose` and critics have `clean | propose`, neither of which has `blocked`, so the "we're reusing existing vocabulary" claim is half-true and the four-of-nine agents that lack the value get a routine-state-machine expansion they don't need. The escape-hatch resolution: define the catastrophic shape as a stand-alone report template (uppercase `STATUS: BLOCKED` first-line header, no routine `Status:` line below) that *replaces* the routine report rather than modifies it. Works uniformly across all agents because the halt shape is its own template, not a value on anyone's existing line. The case-difference (uppercase vs. lowercase) and position-difference (first-line standalone vs. mid-report enumeration value) together signal "this is out-of-band severity, not a routine state." *Learned:* `halt-on-confusion-and-ban-destructive-ops` planning-mode review. The plan's Default justifications framed `STATUS: BLOCKED` as "reuses the existing `blocked` state from every agent's `Status: complete | partial | blocked` enumeration" — but qa-engineer (`pass | fail | propose`) and critics (`clean | propose`) don't have `blocked`. The escape-hatch framing resolves uniformly; the four-of-nine asymmetry would surface as friction the moment a qa-engineer halts on a source-vs-Implementation-log mismatch and has to choose between extending its three-state line and using an unenumerated value.

- **When a harness rule fans out to N agent definitions, identify the load-bearing vocabulary tokens and harden the cross-file consistency check from "consistent" to "verbatim-equal" on those tokens.** A propagation plan typically calls for "consistent wording across files" under its Quality section, which is necessary but underspecified: "consistent" admits paraphrase, "verbatim-equal" doesn't. The risk concentrates on tokens that the dispatching session and downstream agents pattern-match against (report headers, verb pairs, rule citations); paraphrase on those tokens forces the dispatching session to learn N variants of the same canonical token. Identify the load-bearing tokens in planning mode and recommend the Quality bullet name them by name with the verbatim-equality requirement. *Learned:* `halt-on-confusion-and-ban-destructive-ops` planning-mode review. The plan fans rule 9 + rule 16 out to 9 agent definitions, 2 CLAUDE.mds, plan-template, and mental-model. The load-bearing tokens are `STATUS: BLOCKED` (report header the dispatching session pattern-matches against) and `STOP and surface` (verb pair the rule cites by name). The plan's Quality bullet says "rule wordings, the `STATUS: BLOCKED` header, and the concurrency-tolerance phrasing match across every touched file" — the recommendation was to harden this to "verbatim-equal for `STATUS: BLOCKED` and `STOP and surface` specifically," because those two tokens are the ones a future rule refinement would have to update in lockstep across all surfaces.

- **For harness-self plans, distinguish "owning-specialist axis" from "scope axis" in carve-out rules.** When a planning brief proposes a rule with an exemption, check whether the exemption is keyed on (a) which specialist owns the workstream or (b) what the workstream's scope is. The two axes diverge on at least two real cases: code-engineer-led docs work (specialist != docs-engineer, but scope IS docs) and docs-engineer-led API renames (specialist == docs-engineer, scope is API). The user's verbatim directive almost always pins the scope axis ("when the follow-up is explicitly docs additions / fixes" reads scope-not-specialist); the orchestrator's plan often shorthands to the specialist axis because it's mechanically simpler to grep the dispatched specialist from the workstream brief than to parse the scope. The correct planning-mode finding is to pivot the carve-out term to a scope-flavored noun (`docs-scope workstream`, not `docs-pass workstream`) and define it operationally against the workstream brief's stated scope rather than the dispatched specialist. *Learned:* same `qa-engineer-docs-warning-posture` review. The plan's "Default justifications" bullet 2 named "the dispatched specialist is the docs-engineer" as the carve-out trigger; the user's directive named "follow up tasks are explicitly docs additions / fixes" — a scope signal. The amendment was to rename `docs-pass workstream` to `docs-scope workstream` and define membership against the plan brief, not the specialist.

## Gotchas

- **Planning-mode proposals built on unverified identity / aliasing claims need empirical verification before they ship.** When a planning-mode finding proposes a Python-`id()`-based key change (e.g. "widen `id(hp.edges)` to `id(hp.edges._data)` to catch shared-data cases"), the proposal often rests on an implicit empirical claim about which inner objects are aliased across which construction paths. Implementing the proposal without checking the claim can ship a widening that only fires for narrower cases than the brief implied. If the post-impl test-engineer surfaces "the dedup actually doesn't trigger for the natural-constructor case", the right next move is to read the chain (`A.__init__` -> rewrap call -> `B.__init__` -> `_validate_data`) and identify the *one* attribute level whose identity actually survives, then propose the further widening as Workstream H. *Learned:* hiveplotlib GitLab #46 Workstream G shipped `(id(hp.nodes), id(hp.edges._data))` as the dedup key based on a Workstream-F planning-mode finding; empirically `Edges._validate_edge_data` always builds a fresh outer dict so `id(hp.edges._data)` is not aliased across the `HivePlot(nodes, edges)` natural-constructor case. The inner DataFrames within `_data` ARE aliased through the rewrap (assignment is by reference); the right key for full reach is `(id(hp.nodes), frozenset(id(df) for df in hp.edges._data.values()))`. Cross-checked with the notebook prose: the existing `examples/hpm_generic.ipynb` markdown cell promises "the metric is computed once on the shared source data" which the narrower widening doesn't actually deliver. Recommended Workstream H to close the gap.

- **When adjudicating "accept narrow vs. widen further" for a perf-only fix, weight notebook English as the tie-breaker.** The bounded-worst-case argument (Nx slowdown for N cells; metric values stay identical) makes the perf-only fix sound deferrable. But if existing user-facing prose already promises the wider behavior (notebook markdown describing "computed once on shared data" when the code computes per-cell), the prose-vs-code mismatch is itself a correctness concern in the api-critic's lane. Pick (b) recommend-follow-up rather than (a) accept-as-is when the gap exists. *Learned:* same hiveplotlib GitLab #46 Workstream G adjudication. The dedup widening covers same-HP-twice and explicit-aliasing but not the natural constructor case the notebook's English already describes. The notebook's overpromise made (b) the right call even though the per-call cost is bounded.

- **After a tuple-shaped identity key is widened to a set-shaped one, run the "what does collapsing repeated ids change?" check before signing off.** A tuple `(id(a), id(b))` carries multiplicity and order; `frozenset({id(a), id(b)})` loses both. The order loss is usually wanted (dict insertion order across tags shouldn't break dedup); the multiplicity loss is the one to inspect. Concretely: if a user could construct an inner container where the same object appears under multiple keys, the frozenset collapses those into one element and admits dedup collisions with a sibling container that only has the object once. Walk the natural construction paths and confirm none of them produce that aliasing; if none do, log the residual case as low-confidence with a "switch to `tuple(sorted((tag, id(df)) for ...))`" fix sketch in case it surfaces. *Learned:* hiveplotlib GitLab #46 Workstream H widened the dedup key from `(id(hp.nodes), id(hp.edges._data))` to `(id(hp.nodes), frozenset(id(df) for df in hp.edges._data.values()))`. The contrived case `Edges(data={"tag_a": df, "tag_b": df})` (same DataFrame under two tags) collapses to a single frozenset element and would dedup-collide with a `{"tag_a": df}`-only sibling. Verified via `Edges._validate_edge_data` and `HivePlot.add_edges` that nothing in the natural construction paths produces this aliasing; logged as low-confidence rather than must-fix. The bag-vs-set check is cheap; it confirms the residual is pathological rather than realistic before the dedup contract ships.

- **A vocabulary refactor that swaps a one-token noun for a multi-token noun-phrase breaks parallel-clause symmetry; flag the rare parallel-construction sites at planning time rather than waiting for post-impl re-read.** When a refactor replaces `\`\`(nodes, edges)\`\`` with "the ``nodes`` and ``edges`` parameters" across a surface, the high-frequency sites (error messages, ledes, `:raises:` lines) read cleanly. The friction concentrates on the rarer sites where the original one-token noun was *paired with another one-token noun in a parallel clause*: e.g. "the ``(nodes, edges)`` initialization defaults to ... ; the ``graph`` initialization defaults this to ..." mechanically becomes "the ``nodes`` and ``edges`` initialization defaults to ... ; the ``graph`` initialization defaults this to ...", where the conjunction "and" inside the first half competes with the parallel-clause separator and weakens the symmetry the original construction relied on. Recommend in planning mode that the surrounding sentence shape change too — possessive-noun ("the X initialization") to participial-clause ("when initialized with X") — so the parallel form survives the vocabulary swap. Surfacing this at planning time rather than post-impl saves the docs-engineer from re-touching the four parallel sites after the mechanical pass. *Learned:* hiveplotlib GitLab #46 Workstream L planning-mode review. The user-locked vocabulary substitution (drop the `(nodes, edges)` tuple notation in favor of "the `nodes` and `edges` parameters") read cleanly on error messages, ledes, and `:raises:` lines, but the property docstrings on the HivePlot stash side (`hiveplot.py:2163,2169,2171`) and the HPM analog (`hiveplot_matrix.py:617-624`) used parallel constructions where the mechanical substitution made the first clause noisier than the second. Recommended switching to "when initialized with X" framing at planning time so the code-engineer / docs-engineer applied the parallel-preserving rewrite alongside the vocabulary swap on the same pass.

- **When a vocabulary-refactor workstream defers a user-facing sub-surface ("X is docs-engineer's later call"), the post-impl review is the deferral-collection moment, not a free pass to leave it deferred.** A planning-mode dispatch that scopes the sweep to "source + tests + notebooks" and explicitly defers an adjacent user-facing artifact (CHANGELOG entries, migration guides, blog notebooks) to a later docs-engineer pass tends to result in the deferred artifact silently shipping with stale vocabulary, because no follow-up dispatch ever gets created. The post-impl critic is the natural backstop: it's the agent that reads the wiki-plan's `done-when` items against the actual surface state, and a `done-when` item like "the lede paragraph uses the new 'two inputs' framing" implicitly covers any prose that frames the user's headline mental model — including the release notes. When the qa-engineer pre-flags a deferred sub-surface as `worth-discussing`, the api-critic's adjudication should default to **uphold-and-escalate** (must-fix) whenever (a) the deferred artifact ships with the release, (b) the literal phrase load-bears on the user's mental model of the API shape, and (c) the fix is a small mechanical word-swap with no rendering risk. Downgrade only if the deferred artifact is genuinely internal-only, or if the literal phrase is incidental rather than load-bearing. *Learned:* hiveplotlib GitLab #46 Workstream L post-impl. The L code-engineer's Implementation log explicitly noted "CHANGELOG is the docs-engineer / qa-engineer's later call" and the source/notebook sweep completed clean; the qa-engineer caught two CHANGELOG hits (`CHANGELOG.rst:36-37,73-74`) still using the L-locked vocabulary (`passing \`\`(nodes, edges)\`\`` and `Exactly one of the two input shapes is required`) and flagged it `worth-discussing`. The post-impl api-critic upheld and escalated to `must-fix` on the criteria above: the CHANGELOG ships with v0.28.0, both phrases are framing the user's headline two-input-shape mental model in the release-note bullets, and the fix is four word-level edits with zero render risk. The escalation triggered an amend-plan dispatch for a small docs-engineer pass rather than letting the deferral survive into release.

- **Done-when criteria are the post-impl contract; when a Done-when item is unmet, the post-impl review upgrades the qa-engineer's `worth-discussing` to `must-fix` regardless of how qa tagged it.** Workstreams whose dispatch brief enumerates a subset of touched files (e.g., "four locked text drafts across four files" when the plan's Files list and Done-when list cite a fifth surface or a sub-edit inside one of the four) drop the un-enumerated edit silently. The qa-engineer often catches the omission but tags it `worth-discussing` because the qa-engineer reads the Files list and the Implementation log without cross-referencing the Done-when criteria line-by-line. The post-impl api-critic IS the agent that reads the Done-when as the workstream's binding contract; an unmet Done-when item is by definition not a taste call. Practical rule: before signing off the post-impl review, walk each Done-when bullet against the Implementation log and the shipped diff; any Done-when bullet without a corresponding landed edit is `must-fix`. *Learned:* `data-shape-audit-and-feasibility-checks` Workstream A post-impl. The plan's Done-when (line 285) required api-critic.md's planning-mode workflow step 3 to "explicitly check for realistic data construction in the planner's snippets, using 'walk' verb-family phrasing consistent with rule 4." The code-engineer's dispatch brief listed four files; api-critic.md was a fifth touched surface but the brief framed the Workstream around "four locked drafts." The verb alignment on api-critic.md:33 ("demo" → "walk") was caught and auto-fixed by qa-engineer, but the workflow-step-3 bullet addition (the substantive Done-when item) was missed. qa-engineer flagged as `worth-discussing` since the existing bullet "Does the snippet reach for the user-intended path (rule 4)" resolves in spirit; the post-impl critic upgraded to `must-fix` on the Done-when-as-contract criterion. Sibling case to the deferral-collection lesson below, but the trigger is different: deferral-collection escalates when a deferred sub-surface SHIPS with the release; Done-when-as-contract escalates when a Done-when bullet GOES UNMET regardless of shipping context.

- **For a post-impl review on a workstream specifically motivated by closing a semantic-coherence gap surfaced in a prior workstream's post-impl review, the resolution-verdict is the load-bearing output; treat it as mandatory and frontload it above the routine surface-walk.** The post-impl review template carries a structured friction list (must-fix / worth-discussing / low-confidence) suitable for routine surface review, but a "did this close the gap?" workstream demands an additional pass that's distinct from per-call-site friction: explicit comparison against the prior workstream's broken semantic, explicit verification that the round-trip / symmetry / coherence promise the new surface advertises is actually delivered end-to-end across source + tests + docs + notebooks. Practical probe: read the prior workstream's failure-mode description from its post-impl review (or from the amend-plan trigger that spawned the new workstream), then walk the diff asking "is this exact failure mode now closed?" and "does the new surface promise more than the closure, and if so does it deliver on the additional promise?" The verdict is a forced binary (yes / yes-with-caveats / no) plus a one-paragraph rationale; the routine friction list still lands, but the verdict frontloads it. *Learned:* hiveplotlib GitLab #46 Workstream N post-impl. The workstream was specifically motivated by closing the `from_tags(graph=...)` semantic flaw (single-tag collapse) surfaced in Workstream F and preserved through Workstream I's consolidation. The user's task brief made the resolution verdict mandatory; the routine surface walk turned up one low-confidence item (edgeless graph silently produces `(1, 0)` matrix). The verdict was the strong signal; the routine concern was the weak one. Future post-impl reviews on coherence-closure workstreams should match this shape.

- **reST emphasis spans do not parse inline-literal markup, so prose-polish fixes that nest \`\`token\`\` inside `*...*` will render the backticks literally.** When proposing a within-cluster sub-family signal as italicized parenthetical prefixes on the first param of each sub-family (e.g., `*(input-graph conversion sub-family — applies only when graph= is provided)*`), check upfront whether the natural inline-literal references inside the parenthetical will render. They won't: `*(... when ``graph=`` is provided)*` renders with visible backticks. The workable shape is plain text inside the emphasis (`when graph= is provided`) with the trailing `=` doing the kwarg-signaling work; the surrounding parenthetical clarifies it's a kwarg-reference rather than ordinary prose. Also: when the prefix is meant to be read as a *cluster-level header* rather than a per-parameter qualifier, append the literal word "sub-family" to the label — without it, a reader may parse the prefix as a property of the single `:param:` entry rather than as a header for the cluster that follows. The two adjustments (plain-text kwarg token, explicit "sub-family" word) combined make the prefix readable and unambiguous in both source docstrings and rendered autodoc. *Learned:* hiveplotlib GitLab #46 Workstream J extension. The original amendment proposed a lighter blank-line break first and a heavier prefix-style break as the fallback; the blank line was collapsed by autodoc (Sphinx treats consecutive `:param:` entries as a contiguous list regardless of blank lines between them), so the fallback shipped. The code-engineer made two prose adjustments to the amendment's suggested wording — added "sub-family" to disambiguate cluster-level meaning, dropped the inline-literal styling on `graph=` to work around the reST nesting limitation — both of which the post-impl re-review confirmed were the right calls.
