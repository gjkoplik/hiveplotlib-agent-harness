# Expertise: Cross-Cutting & Personal Gotchas

Curated gotchas that **are not owned by any single agent role**: things spanning multiple roles, plus the user's machine, shell, and working-style quirks. Environment notes (WSL/Windows/PowerShell, path/shell boundaries) are the common case but not the only one; anything genuinely cross-cutting belongs here. **Not a log.**

**This file is a fallback, not a catch-all.** Prefer the most specific home for any gotcha: if it belongs to a single role's work (a code/test/docs/viz/qa mistake), it goes in that role's expertise file, even if the user happened to hit it. An entry earns a place here only when it has no better per-role home: either it spans multiple roles, or it is environment/working-style flavored (WSL/Windows/PowerShell quirks, path/shell boundaries, repeated personal working-style corrections). When in doubt, route to the role file. Edit existing entries when a new observation refines or supersedes them; add new entries only when truly new ground is covered; remove entries that no longer earn their place. Every entry comes from a real, observed incident (cite the date or transcript when known), follows the lead + body shape, and stays lean (soft target ~60-90 words) per mental-model rule 11.

Every agent (and the dispatching session) reads this file at task start in addition to any per-role expertise file, per mental-model rule 11. Like the other expertise files, it is read directly from the harness submodule path and is deliberately **not** copied into the consumer's `.claude/` by `sync.sh`. It is maintained partly by the weekly `harness-reflection` scheduled task, which mines recent hiveplotlib session transcripts for recurring friction and proposes additions here.

## Environment

- **WSL symlinks are invisible to Windows-side tools reaching in over UNC paths.** The repo lives in WSL (`\\wsl.localhost\Ubuntu\...`) but is often accessed by Windows-side Claude Code. Symlinks created inside WSL are not followed by Windows tools over the UNC path, which is why `sync.sh` distributes the harness via file copies rather than symlinks. Anything that would otherwise be a symlink across the WSL/Windows boundary must be a real copy.
- **Default shell is Windows PowerShell 5.1, not bash.** Path separators, `$env:VAR` vs `$VAR`, `2>$null` vs `/dev/null`, and the lack of `&&`/`||` chaining all bite scripts written with a POSIX mental model. The Bash tool is available for genuinely POSIX work, but it too runs Windows-side: `cd /home/garyk/...` fails because the WSL filesystem isn't mounted there. Run repo `make` targets and other in-repo commands via `wsl.exe -e bash -lc "cd ~/repos/hiveplotlib && <cmd>"`. Note `bash -lc` (non-interactive login) does not run the conda init block, so `uv` is not on PATH there; call it as `/home/garyk/miniconda3/bin/uv` (observed 2026-06-10). Prefer the dedicated file/search tools over shelling out, which sidesteps the quirk entirely.
- **The `wsl.exe -e bash -lc "..."` string is fragile at both ends: don't lead it with an absolute path, and don't author file content through it.** Git Bash MSYS-rewrites a leading path-like argument before bash sees it: `bash -lc "/home/<user>/tool ..."` arrived as "C:/Program: No such file or directory", and `bash /tmp/script.sh` became `bash C:/Users/.../Temp/script.sh` (2026-07-05, reproducible), so never lead the `-lc` string with `/`; start `cd ~ && ...` and use `~`-relative paths, and invoke scripts from inside an already-running shell string, not as a bare `/tmp/...` argument. Separately, a heredoc inside the double-quoted `-lc` string breaks on the content's own double quotes: `cat >> file << 'EOF'` appended six quote-stripped mangled lines before erroring (2026-07-03), non-atomically corrupting the file. Author content with Edit/Write (UNC path works fine); reserve the bridge for running commands.

- **Glob returns "No files found" over `\\wsl.localhost` UNC paths even for populated directories; use Grep `files_with_matches` for existence and listing checks.** Observed 2026-07-06, reproducible across seven calls (backslash and forward-slash path forms, brace and plain patterns) against directories Read and Grep handled fine in the same session. A false "no files" from Glob silently becomes a wrong "X does not exist" finding. Grep with a cheap content anchor (`.` or `"cells"` for notebooks) and `files_with_matches` lists reliably.
- **Windows-side Edit/Write over the UNC path can flip a WSL repo file to CRLF; sweep `git status` for the warning before reporting.** Observed 2026-07-04: after a session of edits, exactly one touched file (`src/hiveplotlib/viz/datashader.py`) came out with CRLF terminators while sibling files edited the same way stayed LF; `git diff --stat` showed the whole file changed and `git status` printed "CRLF will be replaced by LF". Normalize with `sed -i 's/\r$//' <file>` inside WSL, then re-run `ruff format --check` to confirm content is untouched. Check `git status` output for the warning as a standing end-of-task sweep. Do **not** verify this with a Git-Bash-side `grep -c $'\r'` over the UNC path: it reports a CR on every line even for pure-LF files (observed 2026-08-20 on four files, including ones never touched that session), so it reads as a false positive on everything. Count from inside WSL (`wsl.exe -d Ubuntu -e bash -lc "... grep -c ..."`), or just trust `git status` and a `git diff` that shows only the lines you meant to change.
- **Windows-side Edit over the UNC path can write a NUL byte in place of an inserted space, silently turning a text file binary; never plant a scratch marker to locate an insertion point.** Observed 2026-08-21 on `wiki/wiki/plans/scaling-large-networks.md`: an Edit appending " MARKER" to a paragraph landed the M-A-R-K-E-R but wrote the leading space as `\0`, after which ripgrep reported "binary file matches (found \0 byte)" for every pattern and exact-match Edits against that span failed. Recovery: match text starting after the byte, then re-type the surrounding phrase. Anchor an insertion on adjacent stable text (the next heading) instead, and re-grep the file afterward to confirm it is still text.
- **In a multi-worktree setup, the user-level `hiveplotlib` Jupyter kernel points at ONE fixed venv (some other worktree's), and `tests/pytest_examples.ini` defaults `KERNEL_NAME=hiveplotlib`, so notebook execution in a secondary worktree silently runs against the wrong build.** Override per run by naming the `python3` kernelspec, which each worktree's own `.venv/share/jupyter/kernels/python3` provides (confirm with `.venv/bin/python -m jupyter kernelspec list`: `python3` resolves under the worktree, `hiveplotlib` under `~/.local/share/`). Pytest path: `KERNEL_NAME=python3 .venv/bin/python -m pytest -c tests/pytest_examples.ini -k <stem>`. Direct nbconvert path (re-executing a notebook in place, e.g. a docs output sweep): `.venv/bin/python -m jupyter nbconvert --to notebook --execute --inplace --ExecutePreprocessor.kernel_name=python3 <nb>`. Either way sanity-check the venv resolves `import hiveplotlib` to the worktree source first. The benign `Kernel is running over TCP without encryption` line from nbconvert is not a warnings-as-errors failure. Applies to anyone executing notebooks in a worktree (notebook-author validation, qa close, docs output refresh). Observed 2026-07-06, branch-49 and branch-55 worktrees.

## Working style

_Patterns in how the user likes work done, surfaced from repeated corrections. (Durable preferences belong in the memory dir as `feedback_*` files; this section is for setup-flavored working-style gotchas that recur in practice.)_

- **When iterating on a figure with him, hand over the runnable code (and a rendered image when you can) each round; don't run it internally and narrate conclusions.** In a 2026-06-25 block-matrix design loop he stopped the session twice: "you are neither showing me the picture in the chat nor are you showing me the code... nor can I run it myself because you didn't give me the code," then "just keep spitting out the code to me, and I'll run it myself." He iterates on viz by running it himself; describing intended changes abstractly stalls the loop. Default to surfacing the actual code (and the figure when the surface allows) on every iteration. Distinct from the review-vs-edit rule below: here he is actively co-designing and wants artifacts to run, not silent rewrites.
- **Explain a design with two named scenarios and real numbers before reaching for a rule.** Across the 2026-08-13 branch-53 review he said he was not following four separate times, then unblocked instantly on "default 100, you pass 16": "the numbers simplification helps me understand the abstraction," and he argued in those numbers from then on. The same day, three "not really following you" answers in one message on an abstractly-pitched telemetry proposal. What works: name the concrete inputs, walk case A and case B to their different outcomes, enumerate the candidate options as a short list, and state which one you recommend. Abstract nouns for a thing that has no name yet ("the geometry record", "the resolution chain") are where the confusion starts.
- **Once he says a defect is real and must be fixed, drop de-scope and defer from the option menu.** He stopped a WS8 round with "we're definitely not gonna ignore this because we have to solve this so you can stop suggesting that," having already said three times in the same session that he would rather spend the rounds than ship it wrong ("let's just do this correctly even if it takes a little more back and forth"). His scarce resource is review time, not implementation time, so offering the smaller diff reads as churn. Keep presenting design choices; stop presenting "or we could not."
- **Hand back one complete looped pass, not an in-progress one.** On 2026-08-14 he redirected sequencing: run api-critic and the adversary, fold their must-fixes, then propagate into the notebooks, and only then hand it over. "I don't wanna review something half implemented at any point... have a full complete pass of code fully looped through, then I review code." Notebooks are the slowest surface he reviews, so a code-only handback guarantees a second read of the same work. Finish the gate battery and every downstream propagation first; leave it unstaged and report.
- **Anything you need him to decide has to arrive in chat, in full; the plan is where you write for the agents, not for him.** Four times in-window: "Remember, I'm talking to you not reading the document" and "gonna need more context for the smaller items if you want me to have an opinion on them" (2026-08-18); "the bit that needs to be written for me needs to be surfaced to me in this conversation explicitly, so I'm not opening up a huge document and looking at a subsection of it" (2026-08-18); "can you just make me the relevant jittered scatter plots not in the repo itself, but just right here" (2026-08-21). The corollary he stated outright: never weigh plan or amendment writing against his review budget, because "it's not for me to read, it's for you to read." Restate the decision, the options and your recommendation inline every time, even when the same text already exists in the plan.
- **When the user frames a turn as review ("let me know what you think," "don't make changes," "I'll make the edits"), respond as a reader, not a co-editor.** In notebook and code review threads he drives the edits himself and wants a second set of eyes, not silent rewrites. The jump-to-editing reflex misfires here: in 2026-06 notebook reviews he had to say "that text change was intentional, put it back" and re-issue "don't make any changes yourself" repeatedly inside a single review. Stay read-and-respond until he hands a change back explicitly ("go ahead," "have at it"). Even then the handback covers the edit only, not git state: on 2026-08-07 he interrupted mid-turn with "don't even stage the changes, just make the changes and tell me what's done, and I will review and I will stage," having just taken pushing and committing back as well. Leave the diff unstaged in the working tree and report what changed.

## Recurring mistakes

- **A harness skill shipped mid-session is not reachable in that session; read its `SKILL.md` by path instead of improvising.** On 2026-08-13 he typed `/clarify` at a long-running session (started five weeks earlier) and got "`clarify` isn't among the skills loaded in this session, so I'll just do it directly." Both mechanisms were against it: the skill list is fixed at session start, and `sync.sh` had not yet copied the new skill into the consumer's `.claude/`. When a named skill does not resolve, say why in one line and Read `agent-harness/.claude/skills/<name>/SKILL.md`, which is the source of truth regardless of sync state.
- **A sub-agent that parks on its own background command may never wake; the dispatching session owns the fallback tripwire.** Twice on 2026-07-05 an agent ended its turn "waiting for the background suite/measurement to finish" and was never re-invoked when the child completed; finished work sat silent until the maintainer asked why nothing was moving. When an agent reports it is waiting on a background job, immediately start an independent artifact-based watcher (poll for the output file or process exit from a separate background command) and resume the agent via SendMessage when it fires. Don't trust the agent's own wake-up.

- **A blocked expertise write is intermittent, not structural; retry it instead of parking the lesson in your report.** On 2026-08-09 two sub-agents hit the auto-mode permission classifier on `agent-harness/.claude/expertise/**` (allowed in `settings.json` in both path forms), reported the denial, and preserved the lesson as report text. The maintainer's correction: "the expertise write should have gone through, that's the whole point of expertise files." A third attempt on the same path with unchanged settings succeeded. Retry once before falling back, and if it blocks again report the exact denial *and* the full entry text so the dispatching session can land it from the main session, where the same edit passes.
- **Never split one coherent body of work across separate issues and merge requests on your own initiative; that granularity is the maintainer's call.** An autonomous notebook pass shipped two related notebooks as two issues and two MRs, and he pushed back: "Feel like we never talked about that, and I probably would want it as one." The cause was over-applying a stored preference for parallel off-master MRs that came from an unrelated situation (several independent workstreams). A stored preference is scoped to the situation that produced it. When the work will be reviewed together, default to one branch and one MR, and ask before splitting.
- **Check a scheduled task's `enabled` and `nextRunAt` before warning that it will fire.** A weekly reflection flagged a stale task as about to "fire a stale push at 1:00 AM tomorrow"; it was `enabled: false` and manual-only with no next run, so the alarm was false and the maintainer acted on it anyway. `list_scheduled_tasks` reports both fields. A task existing is not a task scheduled; read its state before predicting its behavior.
- **The system-prompt environment block is frozen at session start; don't trust it to report the current model (or date, or git status) after they change mid-session.** On 2026-07-20 a review was triggered from the phone with `/model claude-fable-5`, but the frozen block still named Sonnet, so the session flagged "did these actually run on Fable?" rather than trusting it, which was the right instinct. Answer from evidence: the on-disk session log tags every assistant message with its serving `model`, so the flip point (a run of `claude-sonnet-5` records giving way to `claude-fable-5` at a user turn) proves which model did which work. Sub-agents launched without a `model` override inherit the session model at spawn, so their model follows from spawn time relative to that boundary. A block existing is not a block that is current.
- **File mtimes inside a copied tree are the source's, not the copy's; reproduce the command instead of inferring history from timestamps.** Diagnosing a stray `build/`, a session read `build/lib` file mtimes spanning nine months and told the maintainer that setuptools rebuilds it on every `make install`. Both claims were wrong: `copy_file` preserves mtimes, so those dates mirror `src/` edit history, and an editable install produces no `build/` at all. Directory mtimes, which are not preserved, showed a single build on a single day. Test a causal claim in a throwaway copy before stating it.
- **When mid-task evidence overturns a claim, sweep the artifacts you already wrote under the old claim.** After that same `build/` investigation reversed twice, the `.gitignore` comment written under the first hypothesis still described an editable install as the source, and the maintainer caught it: "Is the comment on gitignore correct? I thought you were saying something different." Comments, issue bodies, and CHANGELOG lines authored mid-investigation freeze your earlier wrong model. Re-read every artifact you touched before handing off.
- **Harness-generic artifacts must not hardcode the maintainer's name or personal absolute paths; write them agnostically.** The `agent-harness` (and any scheduled task, skill, or template meant to generalize to other repos) is public, reusable content, not Gary-specific. He corrected this twice: 2026-06-29, "take my name out of the agent harness, it's in five places in the CLAUDE.md file, this is meant to be a more generic harness"; and while authoring the weekly-reflection scheduled task, "can these documents, in terms of names and paths, be written more agnostically, leaving out my name and my explicit paths... I want the translation to other repos to be straightforward." Consumer-repo content (a plan, a notebook, this expertise file) can name him and use concrete paths; harness/skill/template content should resolve paths through a variable or relative reference and omit the maintainer's identity.
- **Dispatching session: a design or planning question is an orchestrator trigger, not something to answer inline or bounce to the user.** Twice in 2026-06 the maintainer halted a run with "you're asking me a question you should have asked the orchestration agent" and "I don't see the orchestrator triggering, are you using the harness?" The miss: mid-dispatch a scoping or design question surfaces and the session reasons about it conversationally (or kicks it to the user) instead of invoking the orchestrator in `initial-plan` / `amend-plan` mode. The dispatch-only rule lives in CLAUDE.md; the concrete failure is treating a planning question as chat rather than routing it.
- **Confusion is a stop signal, not a self-recovery signal; concurrent edits are normal, not breakage.** Second agent-destroys-uncommitted-work incident after 2026-05-18: ~2026-05-30 a Workstream M code-engineer hit mid-task blockers and ran `git checkout -- <source files>` to revert its experiment "before reporting back," wiping turns of accumulated uncommitted work (that file was the only copy of upstream edits, not just the agent's experiment). Banning the command treats the symptom; the root cause is the self-recovery instinct. Unexpected state (a file the agent didn't touch, code not matching the brief, an unfamiliar failure) usually means another in-flight agent or the user is actively working, which is a supported mode, not corruption to fix. STOP and report "expected X, found Y"; never normalize state by reverting, or by `Write`-clobbering / re-editing another agent's half-finished work. The destructive-op ban (rule 9, and the `feedback_agents_never_touch_working_tree_state` memory) is the floor; this is the generalization the user asked for after the incident.
- **editorial-critic and viz-critic are read-only (no Edit/Write); never brief them to write their own plan section.** Their tool sets are Read/Glob/Grep (viz-critic also Bash), so a brief instructing them to "write your review into the plan" fails and they correctly halt on the write-back (observed 2026-07-06: an editorial-critic finished a clean review, then reported the write blocked). Collect their reported blocks and record them via one orchestrator `amend-plan` pass (the plan-editing authority), which can disposition their findings in the same pass; api-critic and the adversary DO self-write, since they carry Edit. The critic-completeness gate still requires their sections filled, so the recording hop is not optional.

- **Before you shorten or replace text, name the job it was doing; a rewrite that answers the objection often deletes the point.** Two shapes, one week. (1) *Taking the wrong remedy:* QA offered two fixes for a `construct_curves` note and the session took the one that removed the persistence framing the note existed for, which the maintainer caught with "what was written there was the whole point, and you took out the key thing" (2026-08-20; the session recognized it as the second time that day it treated a critic finding as a verdict rather than an argument). A finding with two remedies is an argument; pick the one that preserves the artifact's purpose. (2) *Compressing to headings:* a shrink of viz-critic's fallback bullets dropped `alpha` 0.4-0.6 (to 0.1-0.2 as density scales 10x), title `y` 1.05-1.15, and node-size-by-area, leaving labels with nothing operative under them. "Losing those alpha numbers is obviously bad" (2026-08-21, restored same day). Compression removes narration, never the numbers or the load-bearing clause.
