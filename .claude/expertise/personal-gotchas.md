# Expertise: Cross-Cutting & Personal Gotchas

Curated gotchas that **are not owned by any single agent role**: things spanning multiple roles, plus the user's machine, shell, and working-style quirks. Environment notes (WSL/Windows/PowerShell, path/shell boundaries) are the common case but not the only one; anything genuinely cross-cutting belongs here. **Not a log.**

**This file is a fallback, not a catch-all.** Prefer the most specific home for any gotcha: if it belongs to a single role's work (a code/test/docs/viz/qa mistake), it goes in that role's expertise file, even if the user happened to hit it. An entry earns a place here only when it has no better per-role home: either it spans multiple roles, or it is environment/working-style flavored (WSL/Windows/PowerShell quirks, path/shell boundaries, repeated personal working-style corrections). When in doubt, route to the role file. Edit existing entries when a new observation refines or supersedes them; add new entries only when truly new ground is covered; remove entries that no longer earn their place. Every entry comes from a real, observed incident (cite the date or transcript when known), follows the lead + body shape, and stays lean (soft target ~60-90 words) per mental-model rule 11.

Every agent (and the dispatching session) reads this file at task start in addition to any per-role expertise file, per mental-model rule 11. Like the other expertise files, it is read directly from the harness submodule path and is deliberately **not** copied into the consumer's `.claude/` by `sync.sh`. It is maintained partly by the weekly `harness-reflection` scheduled task, which mines recent hiveplotlib session transcripts for recurring friction and proposes additions here.

## Environment

- **WSL symlinks are invisible to Windows-side tools reaching in over UNC paths.** The repo lives in WSL (`\\wsl.localhost\Ubuntu\...`) but is often accessed by Windows-side Claude Code. Symlinks created inside WSL are not followed by Windows tools over the UNC path, which is why `sync.sh` distributes the harness via file copies rather than symlinks. Anything that would otherwise be a symlink across the WSL/Windows boundary must be a real copy.
- **Default shell is Windows PowerShell 5.1, not bash.** Path separators, `$env:VAR` vs `$VAR`, `2>$null` vs `/dev/null`, and the lack of `&&`/`||` chaining all bite scripts written with a POSIX mental model. The Bash tool is available for genuinely POSIX work, but one-off commands default to PowerShell semantics. Prefer the dedicated file/search tools over shelling out, which sidesteps the quirk entirely.

## Working style

_Patterns in how the user likes work done, surfaced from repeated corrections. (Durable preferences belong in the memory dir as `feedback_*` files; this section is for setup-flavored working-style gotchas that recur in practice.)_

- **When the user frames a turn as review ("let me know what you think," "don't make changes," "I'll make the edits"), respond as a reader, not a co-editor.** In notebook and code review threads he drives the edits himself and wants a second set of eyes, not silent rewrites. The jump-to-editing reflex misfires here: in 2026-06 notebook reviews he had to say "that text change was intentional, put it back" and re-issue "don't make any changes yourself" repeatedly inside a single review. Stay read-and-respond until he hands a change back explicitly ("go ahead," "have at it").

## Recurring mistakes

- **Dispatching session: a design or planning question is an orchestrator trigger, not something to answer inline or bounce to the user.** Twice in 2026-06 the maintainer halted a run with "you're asking me a question you should have asked the orchestration agent" and "I don't see the orchestrator triggering, are you using the harness?" The miss: mid-dispatch a scoping or design question surfaces and the session reasons about it conversationally (or kicks it to the user) instead of invoking the orchestrator in `initial-plan` / `amend-plan` mode. The dispatch-only rule lives in CLAUDE.md; the concrete failure is treating a planning question as chat rather than routing it.
- **Confusion is a stop signal, not a self-recovery signal; concurrent edits are normal, not breakage.** Second agent-destroys-uncommitted-work incident after 2026-05-18: ~2026-05-30 a Workstream M code-engineer hit mid-task blockers and ran `git checkout -- <source files>` to revert its experiment "before reporting back," wiping turns of accumulated uncommitted work (that file was the only copy of upstream edits, not just the agent's experiment). Banning the command treats the symptom; the root cause is the self-recovery instinct. Unexpected state (a file the agent didn't touch, code not matching the brief, an unfamiliar failure) usually means another in-flight agent or the user is actively working, which is a supported mode, not corruption to fix. STOP and report "expected X, found Y"; never normalize state by reverting, or by `Write`-clobbering / re-editing another agent's half-finished work. The destructive-op ban (rule 9, and the `feedback_agents_never_touch_working_tree_state` memory) is the floor; this is the generalization the user asked for after the incident.
