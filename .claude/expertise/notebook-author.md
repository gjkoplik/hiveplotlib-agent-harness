## Patterns to reach for

_Approaches that work in this role, with the trigger that suggests reaching for each._

- **When a workstream consolidates two API surfaces into one, re-sweep prose in the same pass.** Prose that enumerates both shapes ("available both when X and Y", "regardless of whether you pass A or B", "If you are starting from a Z rather than a W...") earns its keep during the dual-surface period as user-facing disambiguation. After consolidation, that same prose is dead weight: gallery notebooks should pick one canonical form per cell and let the API docs handle cross-shape documentation. The "we still talk about both shapes" framing slips in naturally during a call-site flip pass because the easiest local edit is to swap the API call and keep the prose scaffolding around it. Trigger: any consolidation workstream. Sweep prose in the same pass as the call sites; don't wait for a user to flag it. Earned 2026-05-11 on Workstream I when the user calibrated post-flip prose across seven notebooks that had retained dual-shape framing.
- **When the plan's framing of an algorithm's behavior doesn't match what the algorithm actually does, adjust the markdown to honor the algorithm rather than fudging kwargs to force the plan's framing.** The plan's "Louvain recovers the historical `club` split on Karate Club" framing was a forgivable mis-remembering: default-`resolution` Louvain finds 4 communities on Karate Club, not 2, though each community lives mostly within one club. Two reasonable responses: (a) pass a non-default `resolution=0.5` to force a 2-community result that matches the plan's promised story, or (b) keep default `resolution` and recast the markdown around what Louvain actually produces ("Louvain finds finer-grained substructure than the historical 2-way split, but respects the club boundary as a sanity check"). Option (b) is the right answer because the cell's pedagogical point is "integer labels go directly into `partition_variable`", which the 4-community case demonstrates just as well as a 2-community case would, and the cross-tab telling an honest story is more durable than the cross-tab telling a tidy story. Trigger: when the plan describes an algorithm's behavior and your validation finds the description is approximately-but-not-exactly right. Don't bend the API call to match the plan's prose; bend the prose to match the API behavior, and only halt under rule 9 if the API behavior actually defeats the pedagogical point. Earned 2026-05-25 on Workstream E (`computing_graph_metrics.ipynb`).

## Gotchas

_Surprises not obvious from reading the code, docs, or other agents' definitions._

- **`HivePlotMatrix` doesn't expose `.nodes` / `.edges` at the top level; reach for them through any populated cell.** Every cell in an HPM carries the same underlying `NodeCollection` and `Edges` (the partition slicing happens per-cell at plot time, not at storage time), so any access pattern like a `pd.crosstab` that worked on a `HivePlot.nodes.data` needs to reroute through `hpm[i, j].nodes.data` after the swap. When swapping `HivePlot` → `HivePlotMatrix.from_partition` in a notebook, grep the surrounding cells for `<varname>.nodes.data` / `<varname>.edges.data` references and rewrite each access to go through an arbitrary populated cell (e.g. `hpm[0, 0]` for the canonical diagonal cell). A one-line "every cell carries the same underlying nodes" comment alongside the access keeps the reader oriented; don't gloss over the indirection. Trigger: any HPM swap that also has surrounding cells inspecting the source data. Earned 2026-05-25 on Workstream E amendment 1 re-dispatch (`computing_graph_metrics.ipynb`), where the post-plot Karate cross-tab read `hp_louvain.nodes.data["louvain_communities"]` and needed rewriting to `hpm_louvain[0, 0].nodes.data["louvain_communities"]`.
