# Expertise: Orchestrator

Curated playbook of what this role has learned. **Not a log.** Edit existing entries when a new observation refines or supersedes them; add new entries only when truly new ground is covered; remove entries that no longer earn their place. Every entry earns its line by tracing to a real failure or repeated success.

## Patterns to reach for

- **Plans for the harness itself live in the harness.** When the consumer of a plan is the agent-harness submodule (because the work is changing harness rules, agents, templates, or skills), the plan lives at `agent-harness/.claude/plans/<topic>.md`, not in the parent consumer (hiveplotlib). Symmetry with the consumer convention is the rule: the repo being modified owns the plan. *Learned:* the orchestrator-on-emergent-work plan (the one introducing amend-plan mode and the consumer parameter) was correctly filed in the harness, but the convention had to be invented to write that plan.

- **When post-impl critic findings or scope-changing user asks arrive mid-flight, your job is `amend-plan` mode.** Triage each delta into Added workstream / In-scope tweak / Deferred follow-up, edit the plan's "Plan amendments" section in place, and return a dispatch recommendation. The dispatching session routes the trigger to you under mental-model rule 14; the user does not need to scope the emergent work themselves. The role is "planning specialist," not "single-shot planner at task start." *Learned:* hiveplotlib GitLab #46 Workstream F surfaced a `should-fix` from api-critic and the dispatching session asked the user "should I dispatch a follow-up code-engineer?" — that scoping decision should have routed back here. The harness now codifies the routing (mental-model rule 14, plan-template "Plan amendments" section, consumer trip-wire amendment).

- **When introducing multiple new "modes" for one agent, check whether each candidate mode has independent function or is a parameter switch on an existing mode.** A real mode differs in inputs, outputs, or decision shape (e.g. `initial-plan` produces a new plan file; `amend-plan` reads an existing plan and edits its "Plan amendments" section). A parameter switch reuses an existing mode's function with a different consumer or path. Collapse parameter switches into the existing modes; coining a sibling mode multiplies the surface area the dispatching session has to remember. *Learned:* the orchestrator-on-emergent-work plan's first draft proposed a `harness-meta` mode that was `initial-plan` with `consumer = agent-harness` in disguise; the api-critic's planning review collapsed it to a consumer parameter on the two existing modes, dropping one name from the agent's invocation surface. Mirrors the matching lesson in `expertise/api-critic.md` ("when a plan proposes multiple new modes for one agent, check whether each mode has independent function").

- **After you collapse N modes into N-1 in `amend-plan` mode, the dispatch recommendation must explicitly direct the code-engineer to sweep for residual mentions of the dropped mode name across the agent definition.** A planning-mode collapse closes the Modes section (it now names N-1 modes, not N), but the dropped name typically survives in Output descriptions, parenthetical lists, example invocations, and error messages because those sections describe behavior rather than enumerate modes. Don't assume a rephrase is point-fix only; treat the collapse as a replace-and-sweep across the agent's file. State the sweep direction in the dispatch recommendation explicitly so the code-engineer doesn't have to infer it. *Learned:* the orchestrator-on-emergent-work plan's Workstream A collapsed `harness-meta` into a consumer parameter and the dispatch recommendation framed Workstream A as a structural restructure; the resulting orchestrator.md shipped with the Modes section correctly enumerating two modes but `orchestrator.md:34`'s Output section retained "harness-meta work" as a parallel work-category label. The api-critic's post-impl review re-classified the survivor as a must-fix and the in-scope tweak followed. Mirrors `expertise/api-critic.md`'s post-collapse-sweep lesson from the planning-review side.

- **Every new workstream added in `amend-plan` mode with user-facing API surface needs an `### API Critic — post-implementation review` placeholder under its Implementation summary heading, written when the workstream brief is written.** The placeholder is what the dispatching session reads to invoke api-critic post-impl per mental-model rule 14; without it, qa-engineer's step 12 audit fires `must-fix` and the amend-plan cycle has to repeat just to add the placeholder. Treat the placeholder as a mandatory companion to the workstream brief, not a follow-up. The two existing pages of the plan template (the workstream Implementation summary section and the post-impl placeholder beneath it) are a co-pair; introducing one without the other is the planning-template equivalent of a half-applied diff. *Learned:* in a single hiveplotlib GitLab #46 amend-plan session, Workstream G shipped without the placeholder (qa-engineer flagged `must-fix`, fixed in an amendment), then Workstream H was added in a follow-up amendment and again shipped without the placeholder (qa-engineer flagged the same `must-fix`, fixed in a second amendment). The first miss was a slip; the second turned it into a recurring pattern. The mechanical check is: when you write `## Workstream <X>: <title>` in `amend-plan` mode and the workstream has API surface, in the same edit also append the `### API Critic — post-implementation review\n\nPending — invoke api-critic in post-implementation mode after Workstream <X> ships.` template block under the workstream's eventual Implementation summary heading (or, if the summary doesn't exist yet because the workstream hasn't run, queue the placeholder requirement in the workstream's `Done when` checklist so the implementing session lands it alongside the summary).

## Anti-patterns

- **Pre-deciding which agent runs an amendment workstream.** When you triage an Added workstream into the "Plan amendments" section, name the files and the done-when; do **not** name the specialist who runs it. Dispatch is the dispatching session's call, not yours. The Orchestrator recommends a dispatch sequence in the conversation report; the recommendation is a guide, not an assignment. The same discipline that applies to initial-plan workstreams (mental-model rule 1: "Don't pre-decide which agent runs each; the Orchestrator dispatches" via the dispatching session) applies to amendment workstreams. *Learned:* the inverse of the rule-14 routing lesson — the Orchestrator owning the planning decision does not extend to owning the dispatch decision.
