# Expertise: Orchestrator

Curated playbook of what this role has learned. **Not a log.** Edit existing entries when a new observation refines or supersedes them; add new entries only when truly new ground is covered; remove entries that no longer earn their place. Every entry earns its line by tracing to a real failure or repeated success, and follows the entry shape (lead + body + anchor) and stays lean (soft target ~60-90 words) per mental-model rule 11.

## Patterns to reach for

- **Plans for the harness itself live in the harness.** When the consumer of a plan is the agent-harness submodule (work changes harness rules, agents, templates, or skills), the plan lives at `agent-harness/.claude/plans/<topic>.md` (gitignored), not in the wiki at `wiki/wiki/plans/`. The repo being modified owns the plan, and the harness has no wiki dependency. *Learned:* `orchestrator-on-emergent-work` — the convention had to be invented to file the plan introducing amend-plan mode.

- **When post-impl critic findings or scope-changing user asks arrive mid-flight, your job is `amend-plan` mode.** Triage each delta into Added workstream / In-scope tweak / Deferred follow-up, edit the plan's "Plan amendments" section in place, and return a dispatch recommendation. The dispatching session routes the trigger to you under mental-model rule 14; the user doesn't scope emergent work themselves. The role is "planning specialist," not "single-shot planner at task start." *Learned:* hiveplotlib #46 Workstream F — `should-fix` from api-critic prompted the dispatching session to ask the user "should I dispatch a follow-up code-engineer?"; that scoping should have routed here. Codified as mental-model rule 14 + plan template + consumer trip-wire.

- **When introducing multiple new "modes" for one agent, check whether each candidate has independent function or is a parameter switch on an existing mode.** A real mode differs in inputs, outputs, or decision shape (`initial-plan` produces a new file; `amend-plan` reads an existing file and edits its amendments section). A parameter switch reuses an existing mode's function with a different consumer or path; collapse parameter switches into existing modes rather than coining a sibling that multiplies the surface area dispatching sessions must remember. *Learned:* `orchestrator-on-emergent-work` — initial draft's `harness-meta` mode was `initial-plan` with a consumer switch in disguise; api-critic planning review collapsed it to a parameter. Mirrors api-critic's matching lesson.

- **After you collapse N modes into N-1 in `amend-plan` mode, the dispatch recommendation must explicitly direct the code-engineer to sweep for residual mentions of the dropped name across the agent definition.** The Modes section closes cleanly (N-1 names), but the dropped name typically survives in Output descriptions, parenthetical lists, example invocations, and error messages because those sections describe behavior rather than enumerate modes. State the sweep direction in the dispatch recommendation so the code-engineer doesn't have to infer it. *Learned:* `orchestrator-on-emergent-work` Workstream A — Modes section enumerated two modes correctly but `orchestrator.md:34`'s Output section retained "harness-meta work" as a parallel work-category label; caught post-impl. Mirrors api-critic's planning-side sweep lesson.

- **Every new workstream added in `amend-plan` mode with user-facing API surface needs an `### API Critic — post-implementation review` placeholder under its Implementation summary heading, written when the workstream brief is written.** Without the placeholder, qa-engineer's step 12 audit fires `must-fix` and the amend-plan cycle has to repeat just to add it. Treat the placeholder as a mandatory companion to the workstream brief. Mechanical check: when writing `## Workstream <X>: <title>` for an API workstream, in the same edit append the `### API Critic — post-implementation review\n\nPending — invoke api-critic in post-implementation mode after Workstream <X> ships.` block (or, if the Implementation summary doesn't exist yet, queue the placeholder in the workstream's `Done when`). *Learned:* hiveplotlib #46 — Workstreams G and H shipped without the placeholder in two consecutive amend-plan sessions; the second slip turned it into a recurring pattern.

- **A sub-agent surface-back trigger is by construction a re-triage signal, and the re-triage almost always upgrades the bucket.** When an in-scope tweak is scoped with a "surface back if the fix needs source-side changes" trigger contract and that trigger fires, the original bucket is the one the investigation falsified. Don't re-file the same delta under the same bucket with an "updated dispatch sequence" footnote; that hides the bad scoping and lets the verification gates the new fix needs stay under the lighter bucket. If the re-triaged dispatch spans more than one specialist, it's a workstream — the original tweak entry stays as historical record with a closing "upgraded to Workstream <X>" pointer; its `Done when` / `Out of scope` are superseded, not amended in place. *Learned:* hiveplotlib #46 `TypeAliasForwardRef` Sphinx warnings — scoped as a `conf.py`-only in-scope tweak; docs-engineer's investigation confirmed source-side changes across two files were needed (`TYPE_CHECKING`-guarded import + annotation-quote drops + ty/noqa removals). Upgraded to Workstream M; original tweak entry kept with a closing pointer.

- **When a task brief suggests a specific mental-model rule number OR workstream letter, verify the slot is free against the current canonical surface before locking it in.** Both letter and number sequences are append-only by convention, so a brief written before the most recent cycle can name a taken slot. Mechanical checks: for rules, grep the mental-model SKILL.md for `### <N>\.` headings and pick the next free integer; for workstreams, grep the plan for both `## Workstream <X>` and `### Added workstream <X>` (both shapes coexist after multi-cycle amend-plan) and pick the next free letter. *Learned twice:* (1) `halt-on-confusion-and-ban-destructive-ops` brief proposed rule 15 (taken; corrected to 16); (2) edge-attribute-as-tag brief proposed Workstream J (taken; plan was up to M; corrected to N).

- **A user-endorsed carve-out only pre-covers a later `must-fix` if both are on the *same axis*.** A carve-out for one dimension (amendment 1: Karate may carry two *partition variables*) doesn't cover a finding on a different dimension touching the same dataset, e.g. a *lead-in-vs-body dataset* contradiction where the prose promises a section is "on the toy" but its code runs Karate. Don't wave it off as "already endorsed." Triage test: name the axis the carve-out endorsed and the axis the finding flags; if they differ, it's a separate must-fix, and the amendment should say so. *Learned:* graph-metrics-notebook-restructure WS-A post-impl. The editorial `must-fix` (Per-Metric KA section on Karate while the new switch paragraph promised "remaining sections on the toy") was distinct from amendment 1's Karate-two-ways endorsement; conflating them would have shipped the contradiction.

- **When a lead-in mis-describes a section's dataset but the section's *code* is correct, relocate the section rather than re-cast it, and verify by tracing variable lineage by cell id, not index.** Moving the section into the run that matches its data (option a) beats rewriting working code to chase the prose (option b), which churns a correct demo and risks figure/test fallout. Confirm option a is clean by tracing the governing variable's assignments by stable cell id (e.g. all top-level `G =` cells), not index, since post-edit notebooks renumber. Also re-scan for an *over-absolute* lead-in (a "remaining sections" claim that overreaches a later section legitimately returning to the original dataset) and fold that prose-scoping into the same fix. *Learned:* same WS-A cycle. Option (a) relocated 3 cells with zero in-section changes; cell-id tracing proved `G` was never reassigned across the gap and exposed the deliberate late Karate return that made the lead-in over-absolute.

- **Vocabulary refactors that touch test-asserted strings are added workstreams, not in-scope tweaks — even when the underlying change is "one word."** The triage line is not "is the rewording small?" but "how many specialists does the change span, and does any touch a contract surface that needs its own done-when?" A refactor whose locked strings appear in `match=re.escape(...)` assertions spans code-engineer (source rewording), test-engineer (assertion update), docs-engineer (cross-file sweep), notebook-author (prose sweep), and qa-engineer (full-suite verification) — five specialists co-touching one named contract is the workstream shape. The in-scope-tweak shape fits when a single specialist owns the change against a surface a prior workstream already owns. *Learned:* hiveplotlib #46 — user-authorized "shape" → "inputs" rewording after Workstream I's locked prose review; error messages were test-asserted byte-for-byte. Scoped as Workstream L (added) so the api-critic placeholder landed in its own review subsection; contrast Workstreams J and K extensions, which were single-specialist prose-only follow-ons and correctly in-scope-tweak shape.

- **When a brief proposes "extend an existing rule OR add a sibling rule," check whether the existing rule has substructure that accommodates extension before minting a sibling.** Rules with numbered/lettered substructure (rule 16 has (a) trigger taxonomy, (b) justification, (c) anti-action enumeration, (d) correct action, (e) relationship) extend cleanly: new trigger → (a), new anti-action → (c), rest unchanged. A sibling rule duplicates (b)/(c)/(d)/(e) scaffolding and dilutes the cross-reference surface (every agent definition citing the old rule now has to decide whether to cite the new sibling). The bar for a sibling is real independent function: trigger doesn't share the existing taxonomy, anti-action doesn't share the existing enumeration, or correct-action shape genuinely differs. *Learned:* `rationalization-as-smell` — proposed extend-or-sibling against rule 16; rule 16's (a)/(c)/(e) accommodated the new trigger and anti-action with no other changes. Mirrors the modes-collapse instinct, different surface.

## Anti-patterns

- **Don't pre-decide which agent runs an amendment workstream.** When you triage an Added workstream into "Plan amendments," name the files and the done-when; do **not** name the specialist who runs it. Dispatch is the dispatching session's call. The Orchestrator recommends a sequence in the conversation report as a guide, not an assignment. *Learned:* inverse of the rule-14 routing lesson — owning the planning decision doesn't extend to owning the dispatch decision.
