# hiveplotlib-agent-harness

Skills, agents, commands, and shared mental model for developing hiveplotlib and running research against it. Mounted as a git submodule of hiveplotlib at `hiveplotlib/agent-harness/` (pinned per-consumer, bumpable via `make bump-harness`). Tuned for hiveplotlib's stack (pytest `-n 7`, ruff/ty, 100% coverage, optional-backend markers). Also drives meta-work on itself and on the wiki repo; the orchestrator's Consumer parameter section names the three known consumers.

Distributed into the consumer's `.claude/` by `bash sync.sh`. Defaults to syncing into the parent directory when it looks like a consumer (has `pyproject.toml` or `.claude/`); pass the consumer path explicitly otherwise. Sync uses file copies because WSL symlinks aren't followed by Windows-side tools accessing via UNC paths.

## Trip-wires

- **Halt on confusion; never self-recover or run destructive ops.** See `mental-model` rule 9 for the trigger taxonomy and the absolute ban on destructive operations (no `git checkout -- <path>`, no `git reset --hard`, no `Write` over an un-read file, no silent substitution, etc.).
- **Every plan gets a cold adversarial read.** The `adversary` sub-agent (`.claude/agents/adversary.md`) is mandatory on every plan (it rides on rule 1: a plan exists iff the work is non-trivial). The dispatching session invokes it once per planning layer: a spec-stage pass on the drafted spec before the maintainer signs, a plan-stage pass on the plan *before* grill-me, and post-impl mode on each shipped workstream. It is the structural fix for model sycophancy (grill-me is inline and run by the agreeable dispatching session). Sequencing lives under "Invocation triggers" below.
- **Test name = test body contract.** Shipped artifacts must not carry rationalization prose bridging a substitution against the brief. If an obstacle to the brief surfaces, halt under rule 9.
- **Scratch artifacts go to `/tmp/`, not the project tree.** See `mental-model` rule 16. The working tree is git-tracked space; even untracked PNG dumps, intermediate data exports, and helper scripts clutter `git status` and risk accidental commits during a `git add .`.
- **Workstreams touching CI, publishing, or dependency configuration get qa-engineer's security audit; it must not report `n/a` for them** (`n/a` is the honest default only when no security-relevant surface is touched).
- **Workstreams touching the consumer's library source get qa-engineer's performance check; its tool run must not report `n/a (no executable change)` unless the diff is verifiably docstring/comment-only, and any performance figure the workstream records must name the user-reachable code path it was measured on.**

## Layout

- `.claude/skills/mental-model/`: shared mental model: loaded by the dispatching session; agent definitions and dispatch briefs cite its rules rather than loading it. **Start here.**
- `.claude/skills/viz-quality-bar/`: **hiveplotlib house style only; layered on the external `agent-viz` skill** (`/plugin marketplace add gjkoplik/skills`, then `/plugin install agent-viz@gjkoplik`), which owns the general figure bar. Carries the storytelling-versus-instructional split as this corpus practises it, hive-plot-specific rules, datashader specifics, interactive backends, empirical palette and layout conventions.
- `.claude/skills/hiveplotlib-tutorial-notebook/`: tutorial-style notebook conventions.
- `.claude/skills/hiveplotlib-gallery-notebook/`: gallery-style notebook conventions.
- `.claude/agents/orchestrator.md`: produces plans (`initial-plan` and `amend-plan` modes).
- `.claude/agents/api-critic.md`: dual-role API ergonomics review (planning + post-impl).
- `.claude/agents/research-liaison.md`: wires the dev loop to the research wiki; owns ADR promotion.
- `.claude/agents/code-engineer.md`: implements workstreams.
- `.claude/agents/test-engineer.md`: writes pytest tests, applies optional-dep markers, maintains 100% coverage.
- `.claude/agents/docs-engineer.md`: writes docstrings, autodoc, notebook index entries.
- `.claude/agents/notebook-author.md`: creates or updates `examples/` notebooks. Defers style to the tutorial/gallery skills.
- `.claude/agents/viz-critic.md`: read-only review of rendered figures.
- `.claude/agents/editorial-critic.md`: read-only review of a notebook's structure, scope, dataset coherence, and genre against the notebook skills.
- `.claude/agents/qa-engineer.md`: runs tests/lint/type/doc-build, audits replace-and-sweep, checks Implementation log + CHANGELOG.
- `.claude/commands/`: harness-generic slash-command entry points distributed by `sync.sh` (currently empty; grill-me ships as a skill, and the research track is conversational by design). Consumer-specific commands belong in `<consumer>/.claude/commands/`.
- `.claude/settings.json`: harness-managed Claude Code settings (permissions, enabled plugins). Distributed by `sync.sh`; the consumer's copy is overwritten every sync. See "Settings ownership" below.
- `.claude/templates/spec-template.md`: canonical spec template (the one-page signed intent artifact).
- `.claude/templates/plan-template.md`: canonical plan template.
- `audit.sh`: deterministic qa audits (plan-scaffolding, test-name contract, rationalization markers, CHANGELOG cap) as a script qa-engineer runs and interprets; the prose specs in `qa-engineer.md` define the audits.
- `sync.sh`: copies skills, agents, commands, and settings.json into a consumer's `.claude/`.

## Skill authoring

Three principles bind every skill added or edited here:

- Name the listener's state, not the desired output: a skill description says when it applies, not what it produces.
- Model-invocable vs user-only is a deliberate per-skill authoring choice, made explicitly.
- Skills that fight verbosity fail by growing: the check on every skill edit is simply whether the edit grew the skill.

## Settings ownership

`<consumer>/.claude/settings.json` is harness-managed: `sync.sh` overwrites it from `agent-harness/.claude/settings.json` every run. Consumer overrides (additional `enabledPlugins`, extra `Bash`/`Read` permissions) live in `<consumer>/.claude/settings.local.json`, which `sync.sh` never touches.

Currently shipped: `Edit`/`Write` on `agent-harness/.claude/expertise/**` (for rule-11 expertise updates) in both the consumer-relative and harness-relative forms (`.claude/expertise/**`), so the allowance holds whether a session is rooted at the consumer or at the harness repo itself; `skill-creator@claude-plugins-official` enablement; and the **external viz dependency**, declared as `extraKnownMarketplaces` (`gjkoplik/skills`) plus `enabledPlugins` (`agent-viz@gjkoplik`). See the caveat below: the declaration records the dependency, it does not satisfy it.

**The declaration records the dependency; it does not install it.** Settings marks the plugin enabled and `sync.sh` propagates that, but enabling is not installing: an external-source plugin stays uninstalled until someone installs it. The `extraKnownMarketplaces` entry has not been observed to register the marketplace either; checked from a consumer whose synced settings declare it, `claude plugin marketplace list` did not list `gjkoplik` and the skill was not loadable. Both steps are manual:

```
claude plugin marketplace add gjkoplik/skills
claude plugin install agent-viz@gjkoplik
```

`sync.sh` probes for each and prints whichever is missing, so the gap surfaces at setup time rather than at the moment a figure is being drawn.

Defensive backup: if the consumer's pre-existing `.claude/settings.json` differs from the harness template at sync time, it's copied to `.claude/settings.json.pre-harness-sync.bak` with a warning. Migrate content to `.claude/settings.local.json` and delete the `.bak`.

## The dispatching session

The dispatching session is the consumer-repo Claude Code conversation the maintainer types into. Not a sub-agent, no agent definition. Dispatches sub-agents, surfaces their reports, asks for confirmation between workstreams.

### Invocation triggers

`## Specs and plans` defines the spec artifact and its homes. Plans predating the convention have no spec at all; any gate below that finds no spec says so and moves on.

- **Task start (non-trivial).** First, the **brief-mode gate**: on every non-trivial brief, name whether grill-me's brief mode (pre-orchestrator extraction interview, one question at a time) ran or was knowingly skipped, so a silent non-offer is visible after the fact; the gate outcome lands on the spec's `## Sign-off` intent-extraction line (see `## Specs and plans`), so the record survives the transcript. Offer it when the brief underdetermines the outcome or call shape; the maintainer can also invoke it directly. Then run research-liaison in pre-task mode, then draft the spec (agent-transcribed from the interview record, when one exists, and the brief) and take it through the spec sign-off trigger below. The ordering (brief-mode interview → research-liaison pre-task → spec draft) is deliberate: extraction sharpens what the liaison searches for; if planning judgment prefers another order for a given task, record why. Only after the maintainer signs does the orchestrator run (`initial-plan` mode, with the signed spec path and the liaison findings in the brief); the orchestrator writes the plan; surface the path and pause for review. Work the maintainer decides no spec will govern skips the spec stage: the plan's `Spec:` line reads `none` and every plan-stage gate below still runs.
- **Spec sign-off (code work).** Once the spec is drafted, run grill-me's failure-mode wave into the spec's `## Failure modes`, **before** the spec-stage adversary, so that pass reads a named rubric rather than pushing the old two-invocation problem up a layer. Then invoke the **adversary's spec-stage pass** (premise plus size-and-maintenance / could-this-not-exist; it reports to the dispatching session and writes nothing to the spec) and **api-critic in planning mode** (walks the drafted spec's call shape, each fence with its `Path:` line; reported the same way). Surface the spec and both challenges to the maintainer, who signs or amends: no agent ever signs, and a change the maintainer accepts is folded in by the drafting agent before the signature. **Escalation checkpoint:** an adversary self-tagged `existential-must-fix` here surfaces "reconsider before signing" via the dispatching session before the signature. A knowingly-skipped wave is recorded on the spec's intent-extraction line and leaves the rubric empty by design; the spec-stage adversary then runs rubric-free, working all three angles. Research runs have no spec and skip this trigger: their failure-mode wave stays post-plan inside the grill, per the research-plan shape.
- **Research run against a consumer (conversational).** When the maintainer asks to research something for a consumer ("research whether X"), this is a research run, not a code task. It is invoked **conversationally** (no slash command; a slash command is a deferred option, not built). Invoke orchestrator in `research-plan` mode for the light research-plan shape, then run the bounded shallow-panel research per the `research-track` skill (the conventions home: N disjoint lenses fired as parallel Agent calls, the two standing lenses, two-layer grounding, the binding pre-flight estimate and concurrency ceiling, and the durable landing that follows the consumer). The shared adversary/grill spine applies (rule 18's phase-aware authority; grill-me's research failure-mode branch), same as any plan.
- **Plan produced or substantially amended (non-trivial).** After the orchestrator writes (`initial-plan`) or materially amends (`amend-plan`) a plan, invoke the **adversary's plan-stage pass** (a did-not-author read) *before* offering grill-me: approach plus size-and-maintenance against the workstream set, rubric-aware, since the failure-mode rubric was transcribed from the signed spec at plan creation. On a plan no spec governs this is the plan's only planning pass and works all three angles. This is the plan's legitimacy pass: the plan is challenged before the maintainer invests any grilling. The adversary writes the plan's `### Adversary's challenge`. **Then** offer the maintainer a grill-me alignment pass (recommended for major/long plans), now armed with the adversary's challenge so the grill interrogates its items instead of re-deriving them. Record each grill wave in the plan's `## Alignment (grill)` section; route any resulting change to orchestrator `amend-plan`. When recommending the next dispatch, surface an unfilled `## Alignment (grill)` gate so the maintainer can run it or knowingly skip it. **Pre-grill escalation checkpoint:** when the adversary self-tags a finding `existential-must-fix` (the could-this-not-exist angle landing as "this plan should not exist"), the **dispatching session** surfaces a "reconsider before grilling" checkpoint to the maintainer *before* grill-me, a chance to abort without grilling. Two safety catches: the trigger is the adversary's own tag, not the dispatching session's judgment (so the agreeable hub cannot bury a banger), and the dispatching session surfaces it, not the plan-authoring orchestrator.
- **Plan accepted.** Invoke the named specialist for each workstream as the maintainer green-lights it. When the plan opted into auto-dispatch at acceptance (see "Between workstreams" below), the green-light is the one-time "run it through"; proceed workstream to workstream from there without per-workstream confirmation.
- **Per-workstream spec gate.** Before dispatching implementation for any workstream (not only API-touching ones: a default change, a docs restructure, or a perf claim can move the spec too), the dispatching session posts in chat what a user types to get what this workstream claims, and whether that lines up with the spec's **outcome statement and its call shape**, both quoted from the spec rather than from the plan's transcribed copy: the gate already opens the spec, the spec is short, and quoting the spec is what makes a lossy transcription surface here instead of at plan end (the plan's transcribed copies still stand for their own readers). Quote each `Path:` line along with the snippet it sits under. The question carries its own routing: a mismatch means the spec should be amended (a re-sign), never waived, and a proposed change that narrows the outcome statement is tagged a weakening by the proposing agent and surfaced as one by the dispatching session (the adversary's post-impl spec-check re-grades an untagged narrowing; same two-party shape as the existential-must-fix checkpoint, because the flag cannot rest with the party proposing its own capitulation). The gate rules on its own match and records the ruling in every mode: the posted gate text and the match/mismatch call with a one-line rationale ride the workstream's existing Implementation-log entry as one clause (no second line, same shape as the consumption figures); the adversary's post-impl spec-check re-grades that call, and plan-end qa sweeps the recorded calls. No mode branch: under auto-dispatch the post still happens (the maintainer's absence removes a reader, not a step), a match proceeds without waiting, and a mismatch halts like a `must-fix`. Non-overlap with api-critic's `Benefit-reachability` audit, stated once here: the gate is pre-dispatch, chat-facing, against the spec's outcome statement; the audit is post-impl, agent-facing, against the shipped surface; neither replaces the other. On a plan no spec governs (research plans and plans predating the convention included), the gate post says so and moves on; the log clause reads `n/a (no spec governs this plan)`.
- **Workstream that adds or modifies user-facing API.** Invoke api-critic in post-impl mode after the implementing specialist finishes. Applies to mechanical propagations to sibling classes (e.g., `HivePlotMatrix` mirroring `HivePlot`).
- **Workstream that produces or changes a figure.** Invoke viz-critic in post-impl mode.
- **Workstream that adds or restructures a notebook.** Invoke editorial-critic in post-impl mode after the notebook-author finishes. It reviews the notebook's structure and scope (right notebook, dataset coherence, genre, section-worth); viz-critic covers the figures in the same notebook.
- **Workstream ships.** Invoke the **adversary in post-impl mode** on the shipped artifact, alongside the api-critic / viz-critic / editorial-critic post-impl passes. It attacks the diff blind first, then reads its own `### Adversary's challenge` and the orchestrator's disposition of it (plan-section-as-memory) and reconciles, writing `### Adversary post-impl`. Blind-first is **structural, via a two-message dispatch**: message 1 hands the diff scope plus a scratch extract the dispatching session copies to an absolute path the receiving agent can resolve, named in message 1 (the workstream block under review, its done-when criteria, `## Failure modes`, and `## Holdouts` expected-survivor lists) and **withholds the plan path and the spec path**; after the adversary reports its raw blind findings, message 2 (SendMessage continuation) hands the plan path, the spec path (or the statement that no spec governs this plan), and the workstream's Implementation-log entry for the reconcile and the final `### Adversary post-impl` write. Without the spec path and the log entry, the adversary's two spec-checks (the amendment spec-check and the gate re-grade) are unreachable end to end, and the blind-first contract forbids it fetching them itself. `### Adversary's challenge`, its disposition in `## Plan amendments`, and prior `### Adversary post-impl` history stay off-limits until message 2. (Fallback when the extract was skipped: the adversary honors the contract by Grep offsets + ranged Reads, never a full-file Read in step 1.) A post-impl `must-fix` / `worth-discussing` routes to orchestrator `amend-plan` like the other critics (the planning challenge does not; the maintainer fights that in the grill).
- **Workstream complete.** Invoke qa-engineer for release-readiness verification. If a critic post-impl section is still `Pending` (api-critic, viz-critic, editorial-critic, or the adversary, whose post-impl attack is mandatory on every plan), qa flags `must-fix` and the dispatching session invokes the missing critic before proceeding. The completeness check counts workstreams, not sections, across all four critic sections: for each workstream the Implementation log records as complete, the plan must carry a post-impl block naming it in every critic section that workstream's surface calls for; a filled section missing a completed workstream's block flags the same `must-fix`.
- **Mid-flight emergent work** (post-impl critic finding, or any user ask that would change the workstream set per rule 14). A `must-fix` routes to orchestrator `amend-plan` before any other dispatch. A `worth-discussing` is maintainer-gated: surface it at the checkpoint with a recommendation (amend now / defer / decline) and route only on the maintainer's call, unless it bears on a downstream not-yet-run workstream (then it routes regardless). Under auto-dispatch the maintainer is absent, so a no-downstream-bearing `worth-discussing` batches to plan-end qa instead (see "Between workstreams" below). The orchestrator edits the plan; the dispatching session does not edit the plan directly.
- **All workstreams complete, plan non-trivial.** qa-engineer surfaces a `worth-discussing` ADR-promotion concern. When the maintainer green-lights, invoke research-liaison.

Net sequence with the adversary woven in: grill-me brief mode (optional first step, when a non-trivial brief underdetermines the outcome or call shape) → spec drafted (agent-transcribed) → grill-me failure-mode wave into the spec → adversary spec-stage pass → api-critic walks the spec's call shape → maintainer reads the spec plus both challenges, signs or amends → orchestrator writes/amends the plan from the signed spec → adversary plan-stage pass → grill-me post-plan grill (interrogation waves and delivery shape) → dispatch workstreams, each behind its spec-gate post → adversary post-impl per shipped workstream → qa-engineer.

### Sub-agent discipline

Sub-agents do not invoke other sub-agents. Every invocation comes from the dispatching session. This keeps each sub-agent's context clean, the topology simple, and preserves checkpoint moments between agent calls.

Apparent exception: the orchestrator's `initial-plan` step 2 references research-liaison's pre-task findings. The dispatching session runs research-liaison first and includes the findings in the orchestrator's brief; the orchestrator itself does not invoke anything.

### Between workstreams

Surface the completing agent's report (status, files touched, open questions), name the next dispatch, pause for the maintainer's confirmation. The dispatching session does not implement work itself — reading source, editing code, or running `make` from the dispatching session for a plan-driven task is a process violation.

**Auto-dispatch mode (opt-in, per plan).** Default off; the pause-per-workstream behavior above is unchanged unless the plan opted in. At plan acceptance the maintainer can say "run it through"; the utterance is recorded in the plan's `## Alignment (grill)` section (there is no plan-template marker; the recorded utterance is the opt-in). The dispatching session then proceeds workstream to workstream without the per-workstream confirmation. The per-workstream gate battery (critic post-impl passes, adversary post-impl, qa-engineer) still runs in full; only the pauses are removed. Halt back to the maintainer on:

- any `must-fix`;
- any `STATUS: BLOCKED`;
- a proposed spec change: the signature is the maintainer's in every mode, auto-dispatch included, so the run halts for it like a `must-fix`;
- any finding, `worth-discussing` included, that affects downstream not-yet-run workstreams. The downstream-relevance check is explicit: before proceeding, the dispatching session checks each non-`must-fix` finding (`worth-discussing` and `low-confidence`) against the remaining workstream surfaces. Findings with no downstream bearing accumulate and come back as one batch at plan-end qa; each batched finding is named in the between-workstream report with a one-line rationale for its lack of downstream bearing, so the check is auditable in the mode that removes the maintainer's read.
- a quiet-wrongness clarification (mental-model rule 14, trigger (c)) when remaining workstreams depend on the item; one with no remaining dependents parks as a `## Maintainer questionnaire` item instead of halting.
- **Pre-proceed security check:** for workstreams matching the security trip-wire (CI, publishing, or dependency configuration touched), verify the *checklist component* of qa's `Security audit:` field is not `n/a` before proceeding; a checklist `n/a` there halts back to the maintainer like a `must-fix`. Check the checklist component specifically, not the field as a whole: the tool-run component always carries a result, so a bare field-level check passes vacuously. This check belongs to the dispatching session because it is the party with the trip-wire in context (qa-engineer does not declare this file as an input), and auto-dispatch removes the maintainer's between-workstream read that otherwise catches a mistaken `n/a`.

For an amendment landing before anything has shipped, the dispatching session posts the spec delta (whether the amendment moved the spec, and how) directly in chat: there is no post-impl adversary pass yet for the spec-check to ride.

Fit guidance: mechanical plans (propagations, sweeps, config changes) are good candidates; taste-heavy plans (doc notebooks) keep the pauses. Auto-dispatch is only offered on plans whose spec carries a named failure-mode rubric; a plan with no spec, or a spec whose wave was knowingly skipped and whose rubric is therefore empty, keeps per-workstream pauses, since the post-impl attacks lean on that rubric; this eligibility rule governs offering, not revoking, so a recorded "run it through" opt-in survives mid-flight even where the plan would no longer qualify for the offer.

### Completion reports

Every multi-agent execution (a workstream under a plan, a research run) ends its completion report with agents dispatched, peak concurrency, and approximate token total, naming the estimation basis: sum of subagent usage figures from task notifications where available, otherwise "unknown". Each workstream's consumption line also rides its same-turn Implementation-log append, so the plan-end aggregate reads from the plan file, not reconstructed chat (the figures join the workstream's existing one-line entry, no second line); the never-a-guess honesty constraint binds whoever writes the figures, not just qa-engineer. At plan end, qa-engineer aggregates the per-workstream figures into a plan-total line with the same fields and basis-naming. Open `## Maintainer questionnaire` items are surfaced in every workstream-completion report and at the maintainer's next return, so a parked gate is discoverable without reading the plan file.

### Delivery shape: argue the slicing case

At the grill's delivery-shape step, when a plan crosses roughly three workstreams or its diff plausibly exceeds one reviewable MR, the dispatching session argues the case for sliced MRs under a milestone, on review-cost grounds: a large multi-workstream diff costs weeks of commit-by-commit review, and sliced MRs amortize that cost. Below that threshold, silence. The decision is always the maintainer's, and a keep-together answer is legitimate; the convention exists so the sliced case gets argued, not to flip the single-MR default.

### Low-res header trial

On a plan carrying the trial low-res header (see the orchestrator's initial-plan guidance), dispatch briefs point agents at the header before ranged reads. At that plan's close, plan-end qa reports on how the header was actually used; the maintainer decides whether the header earns a standing place in the template.

## Specs and plans

A **spec** is the intent artifact: one page, signed by the maintainer, stating the outcome in the user's vocabulary and the literal call shape a user types to obtain it. A **plan** is the execution artifact that serves a spec. Templates: `.claude/templates/spec-template.md` and `.claude/templates/plan-template.md`.

Hiveplotlib specs and plans live in the wiki submodule (tracked in the wiki repo, survives across machines). Harness-self specs and plans live under `agent-harness/.claude/` and are gitignored; the harness has no wiki dependency.

Path resolution per consumer:

| Consumer | Spec | Plan |
| --- | --- | --- |
| `hiveplotlib` | `hiveplotlib/wiki/wiki/specs/<topic>.md` | `hiveplotlib/wiki/wiki/plans/<topic>.md` |
| `hiveplotlib-llm-wiki` (planning a wiki-structure change) | `<wiki-repo>/wiki/specs/<topic>.md` | `<wiki-repo>/wiki/plans/<topic>.md` (same physical files as hiveplotlib's paths) |
| `agent-harness` (planning a harness change) | `agent-harness/.claude/specs/<topic>.md` | `agent-harness/.claude/plans/<topic>.md` |

The relationship is **many-to-many**: one spec may govern several plans, one plan may serve two specs, and it lives in the bidirectional links, never in directory structure or slug rules. Sharing a slug is the default convention for the common one-to-one case, not a constraint. A spec closes when its outcome statement is true, which may outlast every plan serving it.

Plans are working scratch, not curated wiki content; `wiki/wiki/plans/README.md` carries the disclaimer for browsers. Specs sit in the opposite register: signed, one page, meant to be read straight through, and `wiki/wiki/specs/README.md` says so for browsers. Drafting a spec in a plan's voice is the one way the artifact fails outright. Major plans promote to ADRs at `wiki/wiki/adr/NNNN-topic.md` per `mental-model` rule 10. Harness-self specs and plans don't promote; the harness CHANGELOG is their durable record.

**Sign-off is the maintainer's act.** Agents draft, transcribe and propose; no agent ever signs a spec change, autonomous runs included. An agent proposing a change that narrows or weakens the outcome statement tags it a weakening when it surfaces the proposal, and the dispatching session surfaces it as one, so a capitulation cannot arrive looking like routine paperwork; the displaced wording moves to the spec's `## Alternatives considered` rather than being deleted. The one qualification to the unqualified statement above, stated where that statement sits: an agent **may** write to a signed spec. A write that **can change what the spec promises** adds an `Unapproved modifications:` line to `## Sign-off` in the same edit, naming what changed; an agent finding the line already present **extends it rather than adding a second**, so there is never more than one; and only the maintainer clears it, by re-signing (adding the marker is the opposite of signing). A write that cannot change what the spec promises fires no marker; the `## Plans` backlink append is the standing example. Any change to a signed spec, at any lifecycle point and mid-implementation included, is a re-sign, and resolving one of the spec's open questions is such a change. A re-sign is a dated event with a record: wiki specs commit the diff; a harness-self spec's record is the chat surface plus a harness `CHANGELOG.md` entry, written by the dispatching session at the re-sign.

**What the call shape and sign-off block carry.** Each call-shape fence carries a `Path:` line stating the class and call chain that snippet takes; that line is where reachability is settled, and it exists to catch two mismatches: a claimed benefit obtainable only through a class the maintainer treats as retired rather than the entry point users are steered toward, and a recorded figure measured on a path the snippet does not take. The per-workstream spec gate quotes each `Path:` line along with the snippet it sits under. The `## Sign-off` fence and the `re-sign, narrowed from:` lines under `## Alternatives considered` are **append-only**; both declarations would otherwise live only in template comments the drafter deletes, and the record of a capitulation needs its protection before the first capitulation. The intent-extraction trail is **one rendered line, not two**, sitting directly above the sign-off invariant sentence, in the placeholder form `Intent extraction: <brief mode ran | knowingly skipped>; <failure-mode wave ran | knowingly skipped>.` The party running the failure-mode wave writes it into the spec's `## Sign-off` at spec stage; where the wave was knowingly skipped, whoever skips it writes the line.

**The issue body, where the work has a tracking issue.** hiveplotlib is on GitLab; harness-self and wiki-structure specs usually have none. That issue's body carries the spec's outcome statement, call shape, and failure modes plus a permalink to the spec file, which stays canonical. The orchestrator regenerates the body at `amend-plan` time and emits the text; the maintainer pastes it. Discussion and multi-party sign-off happen in the issue thread; the spec's `## Sign-off` fence carries the dates and names.

**Write choreography.** The plan file is a single shared file with many writers (grill captures, failure modes, four critic blocks, two adversary subsections, the Implementation log, amendments). Each agent writes only its own named section(s) and never rewrites another agent's; the dispatching session avoids concurrently dispatching two agents that write the same section and serializes Implementation-log appends when workstreams run concurrently. The convention is restated in the plan template where the writers see it.

**Active vs. archived (wiki artifacts only).** New plans start in `wiki/wiki/plans/`. Once a plan's work has fully shipped, it moves to `wiki/wiki/plans/archived/<topic>.md`, so the active directory shows only in-flight work. Listing active plans uses the top-level glob `wiki/wiki/plans/*.md` (excludes `archived/`); resolving a referenced plan checks `archived/` as a fallback. Research Liaison proposes the move; the user confirms and performs it (agents never move plan files). Harness-self plans stay flat. A spec archives on its own trigger, never the plan's: it is not archived when a plan serving it archives, and it is archived when its own outcome statement is true, moving to `wiki/wiki/specs/archived/<topic>.md`. Research Liaison proposes that move too; the user confirms and performs it (agents never move spec files). Harness-self specs stay flat.
